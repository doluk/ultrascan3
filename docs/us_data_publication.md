# us_data_publication — data publication bundles

`us_data_publication` packs a complete UltraScan3 data set into a single
`.tar.gz` file and replays that file into another UltraScan3 installation.
It exists for the moment a data set has to leave the machine it was produced
on: a publication supplement, a hand-over to a collaborator, an archive copy
that has to stay readable when the database does not.

A bundle is self-contained. It carries the project, the experiment, the raw
data, the rotor calibration, the centerpieces, the buffers, the analytes, the
solutions, the edits, the models and the noise records, in the order in which
they have to be re-created, plus a `manifest.yaml` that says what is in it and
what depends on what.

The program is one executable with two front ends. Started without arguments
it opens a window with an **Export** tab and an **Import** tab. Started with
`--mode`, `--no-ui` or `--help` it runs on the command line, without needing a
display.

---

## The dependency chain

Everything the program does follows one order:

```
project → experiment → rawData → rotorCalibration → centerpiece
        → buffers → analytes → solutions → edits → models → noise
```

An export always carries a **prefix** of that chain, so that every record in a
bundle can be re-created from records that appear earlier in the same bundle.
Asking for the models therefore also brings the edits, the solutions, the raw
data, the experiment and the project.

There is one place where the declared order and the real dependency disagree:
raw data cannot be re-created in a target installation without the solutions
its cells and channels refer to. A scope that reaches the raw data is
therefore raised to the solutions, and the program says so in its log:

```
Scope raised from "rawData" to "solutions": raw data cannot be imported
without its solutions
```

Time state data is not a scope of its own. It travels with the raw data of its
run, and can be left out with `--no-timestate` or the **Include time state**
check box.

## IDs, GUIDs and names

A record has three identifying pieces, and they are not interchangeable:

| Record type        | ID key               | GUID key               | Name key      |
|--------------------|----------------------|------------------------|---------------|
| `project`          | `projectID`          | `projectGUID`          | `description` |
| `experiment`       | `experimentID`       | `experimentGUID`       | `runID`       |
| `rawData`          | `rawDataID`          | `rawDataGUID`          | `filename`    |
| `rotorCalibration` | `rotorCalibrationID` | `rotorCalibrationGUID` | `label`       |
| `centerpiece`      | `centerpieceID`      | `centerpieceGUID`      | `name`        |
| `buffers`          | `bufferID`           | `bufferGUID`           | `description` |
| `analytes`         | `analyteID`          | `analyteGUID`          | `description` |
| `solutions`        | `solutionID`         | `solutionGUID`         | `description` |
| `edits`            | `editedDataID`       | `editedDataGUID`       | `filename`    |
| `models`           | `modelID`            | `modelGUID`            | `description` |
| `noise`            | `noiseID`            | `noiseGUID`            | `description` |
| `timeState`        | `timeStateID`        | `timeStateGUID`        | `filename`    |

The **ID** is a database key. It is only meaningful inside the installation the
bundle was exported from, and records read from a local disk store frequently
carry the placeholder `-1`. It is written to the manifest because it makes a
bundle traceable back to where it came from, and for nothing else.

The **GUID** is what an import matches on, and what ties a record to its
parents. GUIDs are generated by the client and travel unchanged: a model
imported into a new database keeps its `modelGUID` and keeps naming the same
`editedDataGUID`.

The **name** is what a person recognizes the record by, and what the conflict
rules compare. `runID` is the name of an experiment, not an ID — a run called
`Demo_2024_Run3` is named, not numbered.

Numeric IDs are never carried over on import. The database allocates its own,
and a local disk store does not use them at all.

## The bundle

A bundle is a gzip-compressed tar archive with `manifest.yaml` at its root and
one directory per record type:

```
bundle.tar.gz
├── manifest.yaml
├── project/<projectGUID>.xml
├── experiment/<runID>.<runType>.xml
├── rawData/<runID>/<runID>.<runType>.<cell>.<channel>.<wl>.auc
├── timeState/<runID>/<runID>.time_state.tmst
├── timeState/<runID>/<runID>.time_state.xml
├── rotorCalibration/<rotorCalibrationGUID>.xml
├── centerpiece/centerpiece_<serial>.xml
├── buffers/<bufferGUID>.xml
├── analytes/<analyteGUID>.xml
├── solutions/<solutionGUID>.xml
├── edits/<runID>/<runID>.<editID>.<runType>.<cell>.<channel>.<wl>.xml
├── models/<modelGUID>.xml
└── noise/<noiseGUID>.xml
```

Payload files are exactly the files UltraScan3 uses in a local disk store, so a
bundle can be opened and read with ordinary tools, and a payload can be dropped
into a data directory by hand if it ever has to be.

### manifest.yaml

The manifest is a deliberately small subset of YAML: a block of scalar header
keys, then one block sequence per record type whose items are flat key/value
maps plus a single nested `depends` map. Every value is quoted.

```yaml
# UltraScan3 data publication bundle manifest
# Records are listed in dependency order; an import replays them top to bottom.
version: 1
created: "2026-09-12T09:30:11Z"
generator: "us_data_publication 4.3.0-dev"
source: "db"
scope: "noise"
bundleGUID: "7f1c2f1e-1d4a-4f2e-9a77-1f0f5d2b6a31"
comment: "Figures 3 and 4 of the paper"
project:
  - projectID: "7"
    projectGUID: "1a2b3c4d-0000-0000-0000-000000000001"
    description: "Lysozyme self-association"
    payload: "project/1a2b3c4d-0000-0000-0000-000000000001.xml"
    sha256: "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
experiment:
  - experimentID: "31"
    experimentGUID: "1a2b3c4d-0000-0000-0000-000000000002"
    runID: "Demo_2024_Run3"
    expType: "velocity"
    label: "Lysozyme, 45 krpm"
    runType: "RA"
    payload: "experiment/Demo_2024_Run3.RA.xml"
    sha256: "5d41402abc4b2a76b9719d911017c592..."
    depends:
      projectGUID: "1a2b3c4d-0000-0000-0000-000000000001"
      rotorCalibrationGUID: "1a2b3c4d-0000-0000-0000-000000000009"
rawData:
  - rawDataID: "41"
    rawDataGUID: "1a2b3c4d-0000-0000-0000-000000000003"
    filename: "Demo_2024_Run3.RA.1.A.280.auc"
    centerpieceID: "2"
    dataType: "RA"
    runID: "Demo_2024_Run3"
    triple: "1.A.280"
    payload: "rawData/Demo_2024_Run3/Demo_2024_Run3.RA.1.A.280.auc"
    sha256: "aaf4c61ddcc5e8a2dabede0f3b482cd9..."
    depends:
      experimentGUID: "1a2b3c4d-0000-0000-0000-000000000002"
      solutionGUID: "1a2b3c4d-0000-0000-0000-000000000007"
timeState: []
rotorCalibration: [...]
centerpiece: [...]
buffers: [...]
analytes: [...]
solutions: [...]
edits: [...]
models: [...]
noise: [...]
```

Header keys:

| Key          | Meaning                                                   |
|--------------|-----------------------------------------------------------|
| `version`    | Manifest format version; this build writes and reads `1`  |
| `created`    | UTC time the bundle was written, ISO-8601                 |
| `generator`  | Program and version that wrote it                         |
| `source`     | `db` or `disk` — where the records were read from         |
| `scope`      | The deepest record type in the bundle                     |
| `bundleGUID` | Identifies this bundle                                    |
| `comment`    | Free text from `--comment` or the **Comment** field       |

Every entry carries a `payload` and a `sha256`. **The digest is the digest of
the payload file**, not of the record's properties, so a bundle can be verified
the way any downloaded file is verified. An import checks every digest before
it writes anything, and refuses a bundle whose payloads do not match.

A section that was in scope but has nothing in it is written as `[]`, so a
reader can tell "exported and empty" from "not exported at all".

## Export

An export reads from the database or from the local UltraScan3 disk store —
whichever the **Disk / DB** selector at the top of the Export tab (or
`--source`) says. When the source is the database, the records are read from
the database: edits, models and noise are downloaded from their database
records rather than picked up from whatever happens to be lying in the local
directories.

### The window

The Export tab works top to bottom:

1. **Export data from** — the disk/database selector. Changing it clears the
   selection, because a run in one source is not the same record as a run of
   the same name in the other.
2. **Select Project** — opens the standard project dialog. At most one project
   can be chosen; choosing one drops any already selected run that does not
   belong to it.
3. **Select Experiment(s)** — opens the run selection dialog. When a project is
   selected the dialog offers only that project's runs; without a project it
   offers everything. Selecting runs is enough on its own — a project is not
   required, and one is adopted from the first run when none was picked.
4. **Experiments, raw data and edits** — a tree of check boxes, `run →
   rawData → edit`. The buttons under it are **All Raw**, **No Raw**,
   **Latest Edit**, **All Edits** and **No Edits**. Checking an edit checks
   its raw data; unchecking raw data unchecks the edits under it.
5. **Selected models and noise** — a second tree, `run → rawData → edit →
   model → noise`, filled by **Select Models…**, which opens the model loader
   pre-filtered to the selected runs. After picking models the program offers
   to select the edits they were fitted to, because a model cannot be imported
   without its edit. Unchecking raw data or an edit that a selected model needs
   asks whether to drop those models or keep the selection.
6. **Noise** — the noise records of the selected models are selected
   automatically. When the *noise dialog* preference is set (UltraScan
   Configuration → Advanced), **Select Noise…** opens the noise loader
   instead so the records can be picked by hand.
7. **Export up to**, **Include time state**, **Comment**, **Bundle file**.
8. **Summary** — the counts of experiments, raw data, edits, models and noise
   records; **Details…** shows the manifest that would be written, without
   copying a single byte of experimental data.
9. **Export Bundle**.

### Command line

```
us_data_publication --mode export --bundle <file.tar.gz> [options]
```

| Option | Meaning |
|---|---|
| `--source db\|disk` | Where the records are read from (default: `disk`) |
| `--project-id <id>` | Export this project, by database ID |
| `--project-guid <guid>` | Export this project, by GUID |
| `--experiment-id <run>` | Export this run; repeatable. Accepts a runID or an experiment database ID |
| `--max-scope <scope>` | Export up to and including this record type |
| `--include-<scope>` | Raise the scope to this record type |
| `--model-guid <guid>` | Export only these models; repeatable |
| `--noise-guid <guid>` | Export only these noise records; repeatable |
| `--no-timestate` | Leave the runs' time state out |
| `--comment <text>` | Store a comment in the manifest |

Without `--experiment-id`, a `--project-id` or `--project-guid` exports every
run of that project.

Examples:

```bash
# Everything about one run, read from the database
us_data_publication --mode export --source db \
    --experiment-id Demo_2024_Run3 --bundle run3_full.tar.gz

# Data only: the chain down to the raw data (and, necessarily, the solutions)
us_data_publication --mode export --experiment-id Demo_2024_Run3 \
    --max-scope rawData --bundle run3_data.tar.gz

# A whole project, models included, from the local disk store
us_data_publication --mode export --project-id 7 \
    --include-models --bundle project7.tar.gz

# What would be exported, without writing anything
us_data_publication --mode export --experiment-id Demo_2024_Run3 \
    --max-scope noise --bundle /dev/null --dry-run --verbose
```

## Import

An import replays a bundle into the database or into a local disk store. The
**Disk / DB** selector at the top of the Import tab (or `--target`) decides
which. The database connection is the one already configured in UltraScan.

**Nothing in the target is ever overwritten.** A record that is already there
is either pointed at or imported again under a new name.

### How a record is matched

For every record in the manifest, in dependency order:

1. **Same GUID already in the target** → that is the same record. It is reused,
   and everything that depends on it is pointed at it.
2. **Name free** → the record is created, keeping its GUID from the bundle. A
   database allocates a fresh ID.
3. **Name taken by a record with a different GUID** → the properties of the two
   are compared. The comparison re-serializes the record already in the target
   in the same canonical form the bundle uses and drops the volatile keys —
   anything ending in `ID`, anything containing `guid`, and the time stamps —
   so that two copies of the same record made in different installations
   compare equal.
   - **Properties match** → the policy decides: `reuse` points at the existing
     record, `rename` imports a renamed copy, `fail` stops the import.
   - **Properties differ** → the record is always imported under a new name.
     Reusing a record that differs would silently change what the imported data
     means, so `reuse` is not offered. `fail` still stops the import.

Renaming changes the name inside the payload and nothing else; the GUID is
untouched, so the record's dependants follow it. Auto-generated names are
`<name> (imported)`, then `<name> (imported 2)`, and so on until one is free.
A run is renamed `<runID>-imported`, and its raw data, edit and time state
files are renamed to match.

### Order of replay

The manifest lists records in the declared section order. The import replays
them in the order the target's own dependencies require:

* **Database:** project, rotor calibration, centerpiece, buffers, analytes,
  experiment, solutions, raw data, time state, edits, models, noise. The
  experiment goes in before the solutions because a database allocates the
  experiment ID a new solution record is first associated with.
* **Disk store:** project, rotor calibration, centerpiece, buffers, analytes,
  solutions, experiment, raw data, time state, edits, models, noise. The
  solutions go in first because the run's experiment XML names them, and that
  file is rewritten as it is written out to name the records of the target.

### Reference data the import does not create

* **Centerpieces** are the reference table an installation ships with, not user
  data. The import matches the bundle's centerpiece against the target's table
  and remaps the serial number; it never adds a row. When the target has no
  matching entry, the run keeps the serial number from the bundle and a note
  says so.
* **Rotors, labs, instruments and operators** are site hardware. A rotor
  calibration is attached to the rotor in the target with the same rotor GUID.
  When an experiment's rotor, instrument or operator is not in the target
  database, the import falls back to the target's first rotor, to the lab's
  first instrument and to the current investigator, and says which substitution
  it made. Check those runs afterwards if the hardware matters to you.

### The window

1. **Import data into** — the disk/database selector.
2. **Select Bundle…** and **Inspect** — unpacks the bundle, reads the manifest,
   verifies every payload digest and fills the contents tree.
3. **Disk Target Folder…** — where a disk import writes. Left empty, the
   UltraScan3 data and results directories are used. Set to a folder, the
   import builds `<folder>/data/...` and `<folder>/results/...` there.
4. **On a name conflict** — the policy, and **Ask me each time**, which opens a
   dialog per conflict showing whether the two records match and offering
   *Use the Existing Record*, *Import Under a New Name* (with the name to give
   it) or *Abort the Import*. The dialog can apply its answer to every further
   conflict of the same record type.
5. **Dry run** decides everything and writes nothing. **Verify payload digests**
   checks the bundle before the first write.
6. **Import Bundle**, then the log and the counts of created, reused and
   renamed records.

### Command line

```
us_data_publication --mode import --bundle <file.tar.gz> [options]
```

| Option | Meaning |
|---|---|
| `--target db\|disk` | Where the records are written (default: `db`) |
| `--output-dir <dir>` | Disk target root; without it the UltraScan3 data and results directories are used |
| `--on-conflict <policy>` | `reuse`, `rename` or `fail` (default: `reuse`) |
| `--on-conflict-<type> <policy>` | The policy for one record type |
| `--rename-suffix <text>` | Suffix for auto-renamed records (default: `imported`) |
| `--no-verify` | Skip the payload digest check |
| `--list` | Print the manifest and stop |

Examples:

```bash
# Into the configured database, asking nothing, renaming anything that clashes
us_data_publication --mode import --bundle run3_full.tar.gz \
    --target db --on-conflict rename --non-interactive

# Into a fresh folder, to look at before committing to anything
us_data_publication --mode import --bundle run3_full.tar.gz \
    --target disk --output-dir ~/inspect/run3

# Reuse matching solutions and buffers, but never reuse a model
us_data_publication --mode import --bundle project7.tar.gz --target db \
    --on-conflict reuse --on-conflict-models rename

# What is in this bundle?
us_data_publication --mode import --bundle project7.tar.gz --list
```

### Common options

| Option | Meaning |
|---|---|
| `--no-ui` | Run without the window (implied by `--mode`) |
| `--db-password <pw>` | Master password for database access. `US3_DB_PASSWORD` is used when this is not given; without either, an interactive run prompts on the terminal |
| `--dry-run` | Decide everything, write nothing |
| `--non-interactive` | Never prompt; fail instead of asking |
| `--verbose` | Report every step |
| `-h`, `--help` | Usage |
| `--version` | Program version |

Exit codes: `0` success, `1` the export or import failed, `2` the arguments
were wrong.

## Round trip

```bash
# On the machine that produced the data
us_data_publication --mode export --source db \
    --experiment-id Demo_2024_Run3 --max-scope noise \
    --comment "Supplement to doi:10.0000/example" \
    --bundle demo_run3.tar.gz

# On the machine that receives it
us_data_publication --mode import --bundle demo_run3.tar.gz \
    --target disk --output-dir ~/ultrascan --verbose
```

The second command prints one line per record and a closing count. Re-running
it reports every record as *reused*: the GUIDs are already in the target and
the payloads already match, so there is nothing left to do and nothing is
written twice.

## Tests

`test/programs/us_data_publication/` builds the non-GUI half of the program
straight into a GoogleTest binary, so the tests exercise the sources the
program ships:

```bash
cmake -S . -B build -DUS3_PROFILE=TEST
cmake --build build --target test_us_datapub
ctest --test-dir build -L us_data_publication --output-on-failure
```

The suite covers the manifest vocabulary and its YAML round trip, the payload
and property digests, the rotor-calibration and centerpiece payload formats,
renaming a record inside its payload, packing and unpacking a bundle, exporting
data only and exporting models with their dependencies, and importing into a
disk store along the create, reuse and rename paths, including the GUID remap
that a reused project forces into the run's experiment XML.
