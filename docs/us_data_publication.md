# us_data_publication — data publication bundles

`us_data_publication` packs a complete UltraScan3 data set into a single
`.tar.gz` file and replays that file into another UltraScan3 installation.
It exists for the moment a data set has to leave the machine it was produced
on: a publication supplement, a hand-over to a collaborator, an archive copy
that has to stay readable when the database does not.

A bundle is self-contained. It carries the project, the experiment, the raw
data, the rotor calibration, the centerpieces, the buffers, the analytes, the
solutions, the edits, the models and the noise records, in the order in which
they have to be re-created, plus a `manifest.yaml` that says what is in it and
what depends on what.

The program is one executable with two front ends. Started without arguments
it opens a window with an **Export** tab and an **Import** tab. Started with
any long option (`--mode`, `--no-ui`, `--help`, ...) it runs on the command
line, without needing a display; arguments without `--mode` are reported as an
error rather than silently opening the window.

---

## The dependency chain

Everything the program does follows one order:

```
project → experiment → rawData → rotorCalibration → centerpiece
        → buffers → analytes → solutions → edits → models → noise
```

An export always carries a **prefix** of that chain: asking for the models
therefore also brings the edits, the solutions, the raw data and the
experiment. That is the order of the export *scopes* -- what a user asks for.
The manifest lists the records in a slightly different order, the one in which
every record depends only on records listed before it (see
[manifest.yaml](#manifestyaml)).

**The project record is the one part that is optional.** It is often not the
exporter's to publish, and the receiving installation usually keeps its own
project list. With `--no-project` (or the **Export the project record itself**
check box cleared) the project is left out, but each run still names it: the
experiment entry keeps `projectGUID` and `projectDescription` as plain
information rather than as a dependency, so an import can attach the runs to a
project the target already has. The scope cannot be the project alone *and*
leave the project out — that would make an empty bundle, and the export says
so.

There is one place where the declared order and the real dependency disagree:
raw data cannot be re-created in a target installation without the solutions
its cells and channels refer to. A scope that reaches the raw data is
therefore raised to the solutions, and the program says so in its log:

```
Scope raised from "rawData" to "solutions": raw data cannot be imported
without its solutions
```

Time state data is not a scope of its own. It travels with the raw data of its
run, and can be left out with `--no-timestate` or the **Include time state**
check box. A time state is two files, the binary `.tmst` and the `.xml` of its
field definitions; a run whose `.tmst` has no definitions cannot be exported
with its time state -- the export stops and says so -- but can be exported
without it.

## IDs, GUIDs and names

A record has three identifying pieces, and they are not interchangeable:

| Record type        | ID key               | GUID key               | Name key      |
|--------------------|----------------------|------------------------|---------------|
| `project`          | `projectID`          | `projectGUID`          | `description` |
| `experiment`       | `experimentID`       | `experimentGUID`       | `runID`       |
| `rawData`          | `rawDataID`          | `rawDataGUID`          | `filename`    |
| `rotorCalibration` | `rotorCalibrationID` | `rotorCalibrationGUID` | `label`       |
| `centerpiece`      | `centerpieceID`      | `centerpieceGUID`      | `name`        |
| `buffers`          | `bufferID`           | `bufferGUID`           | `description` |
| `analytes`         | `analyteID`          | `analyteGUID`          | `description` |
| `solutions`        | `solutionID`         | `solutionGUID`         | `description` |
| `edits`            | `editedDataID`       | `editedDataGUID`       | `filename`    |
| `models`           | `modelID`            | `modelGUID`            | `description` |
| `noise`            | `noiseID`            | `noiseGUID`            | `description` |
| `timeState`        | `timeStateID`        | `timeStateGUID`        | `filename`    |

The **ID** is a database key. It is only meaningful inside the installation the
bundle was exported from, and records read from a local disk store frequently
carry the placeholder `-1`. It is written to the manifest because it makes a
bundle traceable back to where it came from, and for nothing else.

The **GUID** is what an import matches on, and what ties a record to its
parents. GUIDs are generated by the client and travel unchanged: a model
imported into a new database keeps its `modelGUID` and keeps naming the same
`editedDataGUID`.

The **name** is what a person recognizes the record by, and what the conflict
rules compare. `runID` is the name of an experiment, not an ID — a run called
`Demo_2024_Run3` is named, not numbered.

Numeric IDs are never carried over on import. The database allocates its own,
and a record written to a local disk store carries `-1` (see
[Import](#import)).

A few records have no GUID of their own. Those get a **name-based UUID**
(version 5) derived from what identifies them, so that exporting the same
record twice gives it the same identity. Local numbers alone would not do:
calibration 3 of a rotor, or centerpiece 2, is a different record in every
installation that has one, so what the record holds is part of the name, and
two installations only arrive at the same GUID for the same record:

| Record                                | Derived from                                   |
|---------------------------------------|------------------------------------------------|
| time state                            | `timeState:<experimentGUID>`                   |
| rotor calibration without a GUID      | `rotorCalibration:<rotorGUID>:<calibrationID>:<coeff1>:<coeff2>` (coefficients with six significant digits, `'e'`, 5) |
| centerpiece without a GUID            | `centerpiece:<serial>:<name>:<material>:<channels>:<shape>:<maxRPM>:<angle>:<width>` followed by `:<pathlen>:<bottom>` for each row (numbers with 17 significant digits) |

"Without a GUID" includes a GUID column that holds something other than a
GUID. A calibration's identity only uses what its database record and its
local copy agree on, so that it is the same whichever the export reads: the
local file keeps six digits of each coefficient (and both are read as floats),
and the database does not return the calibration experiment's GUID, which is
therefore not part of it. Nor is the date: the database's is when the row was
last written, the local file's when it was copied, so the two sources of the
same calibration would disagree on it. Leaving it out costs no uniqueness that
matters: within one installation the ID alone tells calibrations apart, and
across installations two records only share a GUID when they name the same
rotor and ID and agree on both coefficients to six digits — the same
measurement, copied. For example the calibration 3 of rotor
`44444444-4444-4444-4444-444444444444` with coefficients `1.25e-5` and
`3.5e-10` is always `116899ce-6150-5f54-bdf6-795320a03ae9`, whatever its date.

Bundles written before these rules derived the two from other fields; an
import of an older bundle therefore does not recognise the same calibration
or centerpiece of a newer one by its GUID (it still matches a centerpiece by
name and content).

The time state therefore has a `timeStateGUID` of its own; it depends on its
experiment through `depends: experimentGUID`, and its `timeStateID` is the
database ID of the time state record (`-1` from disk).

## The bundle

A bundle is a gzip-compressed tar archive with `manifest.yaml` at its root and
one directory per record type:

```
bundle.tar.gz
├── manifest.yaml
├── manifest.sha256
├── project/<projectGUID>.xml
├── rotorCalibration/<rotorCalibrationGUID>.xml
├── centerpiece/centerpiece_<serial>.xml
├── experiment/<runID>.<runType>.xml
├── experiment/<runID>.RIProfile.xml                  (RI runs)
├── timeState/<runID>/<runID>.time_state.tmst
├── timeState/<runID>/<runID>.time_state.xml
├── buffers/<bufferGUID>.xml
├── buffers/<bufferGUID>.components.xml               (buffers with components)
├── buffers/<bufferGUID>.spectra.xml                  (buffers with spectra)
├── analytes/<analyteGUID>.xml
├── analytes/<analyteGUID>.spectra.xml                (analytes with spectra)
├── solutions/<solutionGUID>.xml
├── solutions/<solutionGUID>.spectra.xml              (solutions with an extinction profile)
├── rawData/<runID>/<runID>.<runType>.<cell>.<channel>.<wl>.auc
├── edits/<runID>/<runID>.<editID>.<runType>.<cell>.<channel>.<wl>.xml
├── models/<modelGUID>.xml
└── noise/<noiseGUID>.xml
```

Payload files are exactly the files UltraScan3 uses in a local disk store, so a
bundle can be opened and read with ordinary tools, and a payload can be dropped
into a data directory by hand if it ever has to be. Three kinds of file are
added because a local store keeps that information elsewhere, or rounds it:

* `buffers/<bufferGUID>.components.xml` — what the buffer's components are. A
  buffer file names its components by ID and concentration only, and those IDs
  are keys into the installation's component table, which mean nothing in
  another installation. The file has the format of the local
  `etc/bufferComponents.xml` (`<BufferComponents>` with one `<component id
  name unit range gradient_forming>` holding `<densityCoefficients c0..c5>`
  and `<viscosityCoefficients c0..c5>`), with the coefficients written at full
  precision. The definitions are read from the database, or on disk from the
  local component table; a component that is not defined there stops the
  export. Each `<component>` also carries `concentration`: the buffer's
  concentration of it at full precision (`'g'`, 17 significant digits), in
  the order of the buffer's components. The buffer file keeps it to five
  decimals, which makes 5 µM 0.00001 mM; an import takes the value from here
  (`US_DataPubRecords::readBufferConcentrations()`). A bundle written before
  this has no `concentration` attributes, and the buffer file's value is all
  there is.
* `buffers/`, `analytes/`, `solutions/<GUID>.spectra.xml` — the record's
  spectra at full precision. The buffer file writes a wavelength to 0.1 nm and
  a value to five significant digits (two points closer than 0.05 nm fall onto
  one), the analyte file a value to six, and the solution file has no place
  for the solution's own extinction profile at all. The file is

  ```xml
  <!DOCTYPE US_DataPubSpectra>
  <US_DataPubSpectra version="1.0">
    <spectrum type="extinction">
      <point wavelength="280" value="43824.123456789003"/>
    </spectrum>
  </US_DataPubSpectra>
  ```

  with one `<spectrum>` per kind that has points — `extinction`,
  `refraction` and `fluorescence` for buffers and analytes, `extinction`
  (the molar extinction profile) for solutions — and both numbers written
  so that they read back as the same double. It is
  `US_DataPubRecords::writeSpectra()` / `readSpectra()`; the reader refuses
  another root, an unknown or repeated spectrum, a point that is not a pair
  of finite numbers and a wavelength listed twice. A buffer or solution
  without spectra has no such file; an **analyte always has one**, empty when
  nothing was measured, and it holds only measured spectra: from the database
  the profile stored for the analyte, from disk the `<extinction>`,
  `<refraction>` and `<fluorescence>` elements the analyte file really holds
  (`US_DataPubRecords::readAnalyteSpectra()`) — not the 280 nm value
  `US_Analyte`'s reader computes from a protein's sequence. The main payload,
  the library writer's own file, is written with the same measured spectra,
  so it is the same whether the analyte was exported from the database or
  from disk, and it carries no computed point as if it had been measured; an
  import takes the spectra from the spectra payload. A spectrum (of a buffer,
  analyte or solution), a buffer concentration or an analyte amount that is
  not a finite number is refused by the export, as an import would refuse it.
  So is any other numeric value of any staged XML payload: every attribute
  but those that hold text (names, descriptions, labels, run IDs, file
  names, serial numbers, units and GUIDs — `US_DataPub::isTextAttribute()`)
  whose value is `nan`, `inf`, `infinity` (any case or sign) or a number too
  large for a double is refused (`US_DataPub::nonFiniteNumberInXml()`): a
  buffer's pH, density, viscosity or compressibility, a component's
  concentration or coefficients, an analyte's vbar20 or molecular weight, a
  solution's common vbar20, storage temperature or amounts, a model's
  variance, meniscus or component values, a noise vector's values, ...
  A database cannot store such a value, and a disk import would write it
  back as `nan`. In a buffer, analyte or solution it is the run's fault (see
  below); a model or noise record that holds one is left out with a warning,
  or fails the export when it was asked for by GUID.
* `experiment/<runID>.RIProfile.xml` — the radial intensity profile an RI
  (pseudo-absorbance) run is reduced with, in the format of the local
  `<runID>.RIProfile.xml`. On disk it is the file in the run directory; from
  the database it is the profile stored with the experiment record, copied
  byte for byte (only a stored profile that does not parse is written afresh
  from the values read), and read without leaving a copy in the local results
  directory. Only a profile an
  import can read travels: well-formed XML with a `<US_RIProfile>` root and at
  least one `<RI value=...>`. An empty or broken one is left out with a
  warning, and the run is exported without it.

`manifest.sha256` holds the SHA-256 digest of `manifest.yaml` in the format
`sha256sum` writes (`<hex>  manifest.yaml`), so `sha256sum -c manifest.sha256`
checks it. Like the payload digests it guards against a damaged or truncated
bundle, not against someone who rewrites both files.

The archive is built in a private work directory, read back and compared file
by file with what was staged — every name, size and SHA-256 digest of the
content — and only then put in place, in one step: an existing file of the
same name is either left as it was or replaced by a complete bundle, never by
a partial one. The work directory is under the UltraScan `tmp` directory and
holds the staged files, the archive and the unpacked copy at the same time,
so it needs free space of about twice the size of the data plus the size of
the bundle.

Two exports of the same records are not byte-identical: `bundleGUID` and
`created` differ, the gzip header carries a time stamp, and a database export
writes the experiment XML afresh. The payload digests of the records
themselves do not change.

### manifest.yaml

The manifest is a deliberately small subset of YAML: a block of scalar header
keys, then one block sequence per record type whose items are flat key/value
maps plus a single nested `depends` map. Every value is quoted, and the file
is UTF-8. A manifest is at most 64 MiB.

The sections are listed in an order in which **every record depends only on
records of sections listed before its own**:

```
project → rotorCalibration → centerpiece → experiment → timeState
        → buffers → analytes → solutions → rawData → edits → models → noise
```

An experiment names its project and rotor calibration, a time state its
experiment, a solution its buffer, analytes and experiment, a raw-data triple
its experiment and solution, an edit its raw data, a model its edit and noise
its model. A reader can therefore resolve every dependency top to bottom.
(Readers must not rely on the order of the sections in the file, though: the
import replays them in the order its target needs, see
[Order of replay](#order-of-replay).)

Header keys:

| Key          | Meaning                                                   |
|--------------|-----------------------------------------------------------|
| `version`    | Manifest format version; this build writes and reads `1`  |
| `created`    | UTC time the bundle was written, ISO-8601                 |
| `generator`  | Program and version that wrote it                         |
| `source`     | `db` or `disk` — where the records were read from         |
| `scope`      | The deepest record type in the bundle                     |
| `bundleGUID` | Identifies this bundle                                    |
| `comment`    | Free text from `--comment` or the **Comment** field       |

Every entry carries a `payload` and a `sha256`. **The digest is the digest of
the payload file**, not of the record's properties, so a bundle can be verified
the way any downloaded file is verified. An import checks every digest before
it writes anything, and refuses a bundle whose payloads do not match or carry
no digest.

Some records carry **extra payload files**. Each is named by an attribute
whose key ends in `Payload`, and its digest is under the same key with
`Sha256` in place of `Payload`:

| Section      | Extra payload key    | Digest key          | File                                         |
|--------------|----------------------|---------------------|----------------------------------------------|
| `timeState`  | `definitionsPayload` | `definitionsSha256` | the field definitions XML of the `.tmst`     |
| `experiment` | `riProfilePayload`   | `riProfileSha256`   | the RI intensity profile (RI runs that have one) |
| `buffers`    | `componentsPayload`  | `componentsSha256`  | the definitions of the buffer's components, with its concentrations |
| `buffers`, `analytes`, `solutions` | `spectraPayload` | `spectraSha256` | the record's spectra at full precision |

Every payload, extra ones included, always has its digest; a buffer with
components also says how many in `components`.

**A record can depend on several records of one type.** The first dependency
of a type is keyed by that type's GUID key, the further ones by the key with
`_2`, `_3`, ... appended. A solution depends on every one of its analytes this
way (`analyteGUID`, `analyteGUID_2`, ...), and on the experiment of every
exported run whose channels it fills (`experimentGUID`, `experimentGUID_2`,
...).

Every value is written as a double-quoted YAML scalar. `\`, `"`, newline,
carriage return and tab are escaped as `\\`, `\"`, `\n`, `\r` and `\t`; every
other control character (C0, DEL, C1), the Unicode line and paragraph
separators, U+FFFE and U+FFFF, every other noncharacter (U+FDD0–U+FDEF and the
last two code points of each plane) and a surrogate without its pair as
`\uXXXX`, or `\UXXXXXXXX` beyond the first plane. Everything else is written
as UTF-8, so the file holds only what YAML calls printable. A description of any kind — non-ASCII, quoted, over
several lines, with a NUL in it — therefore reads back as it was written; an
export reads the manifest it wrote back and refuses to pack one that does
not.

A section that was exported but has nothing in it is written as `[]`; a
section that was not exported at all is not written. A reader can therefore
tell "exported and empty" from "not exported" without working it out from the
scope. (The project section is left out when the project is, and `timeState`
when the time state is.)

The reader is strict. It refuses a manifest that

* is larger than 64 MiB;
* names no `version`, or one that is not a positive whole number;
* gives a header key or a section twice, or a key twice in one record;
* has a record key other than `depends` with no value (a nested map), or a
  dependency with no value;
* names a payload path (`payload` or any `...Payload`) that is not a plain
  bundle-relative path — absolute, with a drive prefix, a backslash, a colon,
  an empty, `.`, `..` or hidden (dot-first) component, or a component that is
  not a safe file name (below);
* names two payload paths that differ only in case, which are one file on
  Windows and macOS;
* names a `filename` that is not a single safe file name;
* names a run ID (an experiment's `runID`, the `runID` of the records of a
  run) that is not letters, digits, `_` and `-`, at most 80 of them, all of
  the value (a trailing newline is not ignored), and not a Windows device
  name;
* lists the same GUID twice in a section, a dependency that is not in the
  bundle, or a dependency on a section that is listed after the record's own.

A **safe file name** is one that can be created as it is on Linux, macOS and
Windows: no `/`, `\` or `:`; not `.`, `..` or hidden (dot-first); none of
`< > " | ? *`; no control character (C0, DEL, or C1 `U+0080`–`U+009F`) and no
invisible Unicode formatting character (bidirectional overrides, zero-width
characters); no trailing dot or space; not a Windows device name — `CON`,
`PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9` in any case, compared on the
part before the first dot, so `con.xml` is refused too; and at most 255 bytes
in UTF-8.

An unpacked bundle is also refused when it holds a symbolic link or anything
that ended up outside the bundle's own directory.

## Export

An export reads from the database or from the local UltraScan3 disk store —
whichever the **Disk / DB** selector at the top of the Export tab (or
`--source`) says. When the source is the database, the records are read from
the database: edits, models and noise are downloaded from their database
records rather than picked up from whatever happens to be lying in the local
directories, and nothing is written into the local data or results
directories.

**An export either is complete or fails.** It writes no bundle, and the
command line exits with `1`, when

* there would be nothing in the bundle;
* a run, raw data, edit, model or noise GUID it was asked for by name matches
  nothing (`--model-guid`, `--noise-guid`, or the selection of the window);
* a run belongs to a project other than the one `--project-id` /
  `--project-guid` names;
* none of the selected runs has raw data, at a scope that reaches the raw data
  (a single run without raw data is only a warning);
* a record it needs cannot be read: the experiment, a solution together with
  its buffer and analytes, a raw triple's solution (only when the solutions
  are exported — an export of the experiment alone names what it can), the
  rotor calibration the run names, a centerpiece that is not in the
  centerpiece table, a buffer component that is not defined, a time state
  whose definitions are missing, or any payload; on disk a missing project
  file says to leave the project out with `--no-project`. (A calibration,
  centerpiece, solution or time-state definitions that are not there is the
  run's own fault: a project export leaves the run out, see below. A
  database or table that cannot be read fails every export.);
* a raw data record or an edit downloaded from the database is not the record
  the catalog listed: the GUID in the `.auc` header, or the `editGUID` and
  `rawDataGUID` of the edit, differ from the ones it is exported under (an
  import would refuse the bundle for it);
* a noise record asked for with `--noise-guid` (or ticked in the window)
  belongs to a model that is not in the bundle;
* the bundle would be refused on import. The export applies the import's
  acceptance rules — the same functions of `US_DataPub`, so the two cannot
  drift apart — before it packs anything:
  * every record's GUID, and every GUID it depends on, is a GUID: 8-4-4-4-12
    hexadecimal digits, the whole value (`US_DataPub::guidIsUsable()`);
  * inside every XML payload, every attribute that names a record by GUID —
    `guid`, anything ending in `GUID`, the `value` of an element ending in
    `GUID` — is empty or a GUID (`US_DataPub::unusableGuidInXml()`). A legacy
    record with, say, an operator GUID of `7` stops the export with the value
    named;
  * a run type is one to eight letters or digits
    (`US_DataPub::runTypeIsUsable()`);
  * raw data, edits and the time state are named `<runID>.…` after the run
    they depend on (`US_DataPub::runFileNameIsUsable()`), and the time state
    is `<runID>.time_state.tmst` with its definitions.

  `US_DataPubManifest::checkAcceptance()` applies them to the manifest, a
  preview included;
* just before packing, the staged tree is not exactly `manifest.yaml`,
  `manifest.sha256` and the payloads the manifest names, or a payload no
  longer matches its digest. A payload that cannot be read to its end gets
  no digest at all (`US_DataPub::fileSha256()`), so a short read stops the
  export rather than carrying the digest of half a file.

**A run of a project export that breaks a rule is left out** rather than
failing the whole export: a project with a run whose run ID, run type, or the
GUID or file name of one of its triples or edits cannot be exported goes
without that run, with a warning naming it. So does a run whose records turn
out not to hold together while they are staged: a channel without a solution
(or whose solution, buffer or analyte is gone), a rotor calibration or
centerpiece the run names that the source does not have, a time state
without its field definitions, a payload that does not carry
the GUID the catalog lists it under, an experiment XML that names another run
ID or GUID than the run (a run directory renamed by hand), a spectrum or
other value that is not a finite number, or an experiment, raw data or edit
that another run of the export already brought into the bundle (a run
directory copied under another name, GUIDs and all: the run that comes
later is taken for the copy, and the one already staged keeps everything).
Everything already staged for that run is taken back, and so are the
warnings its records gave: the files it staged first, and only those (the
staging directory keeps a list of what it hands out, so taking a run back
costs what staging it did, not a walk of the tree). A record the run shares
with a run after it — a solution, a calibration — goes too, and the later
run stages it again. Its models and their noise stay out with it —
those whose edit is not in the bundle: a model fitted to an edit that
another run brought in (the same edit GUID, in a copied run directory)
stays. A model or noise record that was asked for by GUID
(`--model-guid`, `--noise-guid`) whose run is left out fails the export
instead of vanishing from it. A database or disk that fails is not the
run's fault and still fails the export. A run named on its own
(`--experiment-id`, or picked in the window) is refused instead. When no run
of the project is left, the export fails.

Records the export cannot carry and was not asked for by name are left out
with a warning: a model or noise record without a GUID, a noise record whose
model is not in the bundle, an RI profile that does not parse.

**What an export leaves out is always reported.** The command line writes
each warning as a `Warning: ...` line on the error output, with or without
`--verbose`, and its last line on the standard output counts what was left
out:

```
Wrote 16 records to project5.tar.gz (left out: 1 run(s), 0 other record(s); see the warnings)
```

(A dry run says the same in its "would be exported" line.) Nothing left out,
no such count.

**A dry run, and the window's preview, are the export without the bundle.**
They read and stage every record in a staging directory of their own and make
every check the export makes — the payload GUIDs, the experiment XML, values
that are not finite, the staged tree — and remove the directory afterwards, so
the records they list, their digests and what they leave out (which copy of a
copied run directory, say) are what the export writes. They take as long as
the export, less the packing. The window's completion box (and the preview, and the box of
an export that failed) lists the runs left out, the number of other records
left out, and the warnings. `US_DataPubExporter::warnings()`,
`leftOutRuns()`, `leftOutRecords()` and `warningReport()` give the same to a
caller.

A run whose database record names no rotor calibration is exported without
one; the rotor's first calibration is not assumed in its place, since a rotor
is recalibrated over the years. (The experiment XML that `US_Experiment`
writes still names the calibration it reads for such a run.)

The staged experiment XML names the run's rotor calibration by its GUID as
well as by its ID: `<calibration id="…" guid="…" …/>` (`US_Experiment`
ignores the attribute). A disk store a bundle is imported into gives the
calibration no ID of its own (`-1`), so the ID alone named nothing there, and
a run exported from it again — database → bundle → disk → bundle — lost its
calibration. An export from disk finds the calibration by that GUID among the
`C*.xml` files of the rotor directory when the ID does not find it.

A model's variance and meniscus travel with every digit: in the manifest
(`variance`, `meniscus`, from the database row when the source is a
database) and in the staged model XML, where `US_Model` writes six digits —
or none, when the stored XML did not have them. A disk import, which has only
the payload, keeps what the database row had.

A time state from the database is always staged as
`<runID>.time_state.tmst` with its `<runID>.time_state.xml`, whatever file
name the record keeps, because an import takes only a run's files whose names
start with `<runID>.`.

**Only what the selected triples need is exported**: the solutions and
centerpieces of their channels, not every one the experiment ever had. On disk
the run's experiment XML keeps the `<dataset>` entries of the triples the
bundle carries and no others: those of deselected triples, and those whose
`.auc` file is no longer there, are left out of the copy (the latter with a
warning). When nothing has to go it is copied as it is. A database export writes the experiment XML afresh from
the selected triples. Either way the experiment XML names the investigator and
operator of the run by GUID, as it does in a local store; a bundle that is to
be published should be checked for that.

Runs of several projects can be exported together; each project the runs
belong to is then in the bundle, and each experiment depends on its own. A run
named twice is exported once.

A model with no noise of its own borrows the newest noise of its edit that
existed when the model was made (see the window, below). On disk the time
stamps compared are those of the files, so the choice can depend on when the
files were copied; the database keeps the time each record was written.

The walk of the record chain — experiment, raw data, edit, model, noise — is
`US_DataCatalog` in `utils/`, the same one `us_manage_data` browses with, so a
bundle sees exactly what the data manager sees. It is read in two layers: the
experiments are listed first, and the chain of one experiment is read when the
export needs it. Against the database that is a handful of per-experiment
queries; on disk it is one pass over the store, with the model and noise
directories read once rather than once per triple. What `us_data_publication`
adds on top is what only a publication needs: the project list, the experiment
XML of a run — which is where a disk store records its rotor calibration,
centerpieces and solutions — and the run's time state.

**A database that has not been updated still works.** Those per-experiment
queries are stored procedures added for the catalog; against a server that does
not have them the catalog notices, says so, and falls back on the procedures
UltraScan has always had — one query per record. The bundle that comes out is
identical, it just takes longer to collect. Exporting one run of a
multi-wavelength experiment from the test database took 5.5 s with the new
procedures and 54 s without them; for a publication, which is a handful of runs
rather than a whole store, that is a wait rather than a problem.

### The window

The Export tab works top to bottom:

1. **Export data from** — the disk/database selector. Changing it clears the
   selection, because a run in one source is not the same record as a run of
   the same name in the other.
2. **Select Project** — opens the standard project dialog. At most one project
   can be chosen; choosing one drops any already selected run that does not
   belong to it.
3. **Export the project record itself** — clear it to leave the project out
   of the bundle. The runs still name their project, so an import can attach
   them to a project the target already has.
4. **Select Experiment(s)** — opens the run selection dialog. When a project is
   selected the dialog offers only that project's runs; without a project it
   offers everything. Selecting runs is enough on its own — a project is not
   required, and one is adopted from the first run when none was picked.
5. **Experiments, raw data and edits** — a tree of check boxes, `run →
   rawData → edit`. The buttons under it are **All Raw**, **No Raw**,
   **Latest Edit**, **All Edits** and **No Edits**. Checking an edit checks
   its raw data; unchecking raw data unchecks the edits under it.
6. **Selected models and noise** — a second tree of check boxes, `run →
   rawData → edit → model → noise`, filled by **Select Models…**, which opens
   the model loader pre-filtered to the selected runs. After picking models the
   program offers to select the edits they were fitted to, because a model
   cannot be imported without its edit. Unchecking raw data or an edit that a
   selected model needs asks whether to drop those models or keep the
   selection.
7. **Noise** — every noise record of every selected model is ticked
   automatically; untick the ones that should stay out. Unticking a model
   unticks its noise with it, and ticking a noise record ticks its model back
   on, because noise cannot travel without the model it belongs to.
   **Reload Noise** looks the records up again.

   A model with **no noise of its own** is not left without any. Noise is
   fitted to an edit, and a model made afterwards is run with the noise that
   was already there, so such a model travels with the newest noise of its
   edit that existed when the model was made — one record of each type, since
   a run can carry a time-invariant and a radially-invariant record at once.
   Those rows are marked *(of this edit)* in the tree. The record still
   belongs to the model it was fitted to — its payload names that model — so
   that model travels too (the log says so), the noise depends on it in the
   manifest (`depends: modelGUID`), and every model of the bundle it is
   carried for is in `borrowedByModelGUIDs` (separated by spaces) — also one
   whose noise is listed first for the model it was fitted to. Which noise a
   model without any of its own was run with is otherwise known only from the
   records' time stamps, which a target that writes the records anew need not
   keep; an import that writes such a model before the noise loses the
   relation unless it reads this. When the model it was fitted to cannot travel (it is
   gone, or its edit is not in the bundle) the noise stays out with a
   warning, or fails the export when it was asked for by GUID.
8. **Export up to**, **Include time state**, **Comment**, **Bundle file**.
9. **Summary** — the counts of projects, experiments, raw data, edits, models
   and noise records. With only a project picked and no run selected, there
   is no tree to narrow anything down: every run of the project goes, with
   everything it holds up to the scope, as `--project-guid` does on the
   command line, and the summary says so. **Details…** shows the manifest that would be written,
   with the warnings of what would be left out: it is the export without the
   bundle (every record is read and checked, in a staging directory that is
   removed afterwards), so it takes as long as the export. **Latest Edit** ticks
   the edit with the latest edit time stamp of each triple.
10. **Export Bundle**. While the export runs the tab cannot be changed, the
    Import tab cannot be opened, and closing the window waits: it closes once
    the export is done. The same holds the other way round during an import.

### Command line

```
us_data_publication --mode export --bundle <file.tar.gz> [options]
```

| Option | Meaning |
|---|---|
| `--source db\|disk` | Where the records are read from (default: `disk`) |
| `--project-id <id>` | Export this project, by database ID |
| `--project-guid <guid>` | Export this project, by GUID |
| `--experiment-id <run>` | Export this run; repeatable. Accepts a runID or an experiment database ID. A run ID that matches exactly always wins — a run ID made only of digits is not taken for another run's database ID (that is warned about) — and a database ID is only taken when exactly one run has it |
| `--max-scope <scope>` | Export up to and including this record type (default: `noise`, the whole chain) |
| `--include-<scope>` | Export up to and including this record type; with several, the deepest counts. It may not go beyond `--max-scope`; within it, it is what is exported (`--max-scope noise --include-solutions` exports up to the solutions) |
| `--model-guid <guid>` | Export only these models; repeatable |
| `--noise-guid <guid>` | Export only these noise records; repeatable |
| `--no-timestate` | Leave the runs' time state out |
| `--no-project` | Leave the project record out; the runs still name it |
| `--comment <text>` | Store a comment in the manifest |

An import option (`--target`, `--output-dir`, `--on-conflict…`,
`--rename-suffix`, `--no-verify`, `--strict-hardware`, `--list`) given with
`--mode export` is refused with exit code `2`, as is an export option with
`--mode import`; `--project-guid` and the common options are taken by both.

Without `--experiment-id`, a `--project-id` or `--project-guid` exports every
run of that project. With both, every run named has to belong to that project.
At least one of the three is required. A `--dry-run` needs no `--bundle`.

Examples:

```bash
# Everything about one run, read from the database
us_data_publication --mode export --source db \
    --experiment-id Demo_2024_Run3 --bundle run3_full.tar.gz

# Data only: the chain down to the raw data (and, necessarily, the solutions)
us_data_publication --mode export --experiment-id Demo_2024_Run3 \
    --max-scope rawData --bundle run3_data.tar.gz

# A whole project up to the models (no noise), from the local disk store
us_data_publication --mode export --project-id 7 \
    --include-models --bundle project7.tar.gz

# What would be exported, without writing anything
us_data_publication --mode export --experiment-id Demo_2024_Run3 \
    --dry-run --verbose

# From the database in a script, the password in a file only you can read
us_data_publication --mode export --source db --non-interactive \
    --db-password-file ~/.us3_master --experiment-id Demo_2024_Run3 \
    --bundle run3_full.tar.gz
```

## Import

An import replays a bundle into the database or into a local disk store. The
**Disk / DB** selector at the top of the Import tab (or `--target`) decides
which. The database connection is the one already configured in UltraScan.

**Nothing in the target is ever overwritten.** A record that is already there
is either pointed at or imported again under a new name. In a disk store, a
file of a run directory that is already there is reused only when it is the
file the import would write; a time state only when its field definitions are
there beside it and are the bundle's too. Anything else stops the import, and
so does a file that cannot be compared, with the reason. A run directory's
experiment XML is the `<runID>.<runType>.xml` whose run type is one to eight
letters and digits, so an RI run's `<runID>.RIProfile.xml` is never taken for
it.

### What is checked before anything is written

A bundle is data from another installation — or from anyone — so it is
checked as a whole first, and refused as a whole when any check fails:

* **Paths.** Every `payload` and every time state's `definitionsPayload` has to
  be a relative path inside the bundle: no leading `/`, no `..`, no
  backslash, and no symbolic link that leads out of it.
* **Run IDs and file names.** Every run ID — the bundle's, a renamed one, one
  typed into the conflict dialog — has to be a usable run ID: letters, digits,
  `_` and `-`, at most 80 characters (the rule `US_ConvertIO` applies to run
  directories, checked against the whole text, so not even a trailing newline
  passes). A run type is one to eight letters and digits, again on the whole
  text. Every file name the import writes has to be a single name that is safe
  on every platform (`US_DataPub::isSafeFileName()`), and every raw data, edit
  and time state file name has to start with its run ID; a time state is always
  `<runID>.time_state.tmst` with its `.xml` definitions.
* **GUIDs.** Every GUID the manifest names — a record's own and every one in
  its `depends` — and every GUID inside a payload (an attribute `guid` or
  `...GUID`, or the `value` of an element such as `editGUID`) has to be a GUID:
  hexadecimal digits in groups of 8-4-4-4-12 and nothing else.
* **Digests.** The manifest has to match `manifest.sha256`, and every payload
  has to match its digest -- the main payload of each record and every extra
  one (a time state's field definitions, an RI intensity profile, a buffer's
  component definitions); a digest is compared without regard to the case of
  its hexadecimal digits. A payload without a digest fails the check too;
  `--no-verify` (or unchecking **Verify payload digests**) is the only way to
  import such a bundle.
* **Contents.** Every payload has to parse as the record type the manifest
  gives it, and has to carry the GUID the manifest gives it — including the
  `rawGUID` inside an `.auc` file and the `editGUID` and `rawDataGUID` inside an
  edit. The library writers update a record by the GUID inside its payload, so
  a payload naming another record could otherwise overwrite that one.
* **Dependencies.** Every buffer and analyte a solution names, the model a
  noise record names, the edit a model names (whether or not the manifest
  lists it as a dependency), the raw data an edit belongs to and the solution
  of every triple of a run has to be in the bundle or already in the target.
* **Owners** (database). A project, solution, raw data, edit, model or noise
  record the import would reuse, or attach a record of the bundle to, has to
  be in the bundle or be one of the current investigator's own. The GUID
  lookups the database offers do not see to that: `get_editID`,
  `get_modelID` and `get_noiseID` (like `get_bufferID` and `get_analyteID`)
  find a record whoever owns it, and `get_projectID_from_GUID`,
  `get_solutionID_from_GUID` and `get_rawDataID_from_GUID`, which check the
  permission of the person logged in, find anyone's for an admin. So every
  such record is checked against the investigator's own listing
  (`get_project_desc`, `all_solutionIDs`, `all_rawDataIDs`,
  `all_editedDataIDs`, `get_model_desc`, `get_noise_desc`), and a record of
  someone else's stops the import before anything is written. Buffers and
  analytes are chemistry the investigators of a database share, and are
  reused whoever entered them.
* **Buffer components.** A buffer's component definitions are read and checked
  here, before anything is written (see *Buffer components* below). A bundle
  of the older format, which carries no `componentsPayload`, is refused when
  one of its buffers names components: a component ID of the exporting
  installation means nothing without its definition.
* **Runs** (database). The bundle's runs are looked up in the target now,
  before the transaction opens (see *How a record is matched*); a run that
  another investigator holds stops the import.
* **The chosen project** (below) has to exist in the target, and in a database
  belong to the current investigator.

### One transaction in a database

A database import runs in a single transaction on one connection. It is
committed once every record is in, and rolled back on any failure, so a failed
import leaves the database as it was. That holds within what a MySQL
transaction can promise: the tables written are InnoDB, and no stored procedure
commits by itself. A statement that does commit ends the transaction on the
server; the commit (or rollback) that follows then fails, and the import says
that some records may have been kept rather than that nothing was imported.

Every lookup that can be made in advance is made before the transaction
opens, so that it is held open for the writes and little else: every record of
the bundle by its GUID, the investigator's listings and the name indexes made
from them, the fingerprints of the records a name conflict compares with, the
buffer component table, the labs, rotors, calibrations, instruments and
centerpieces, the rotors and operators the runs and calibrations name, the
project a run names when the bundle carries none, and the names a renamed run
would try. What is left to the transaction is what depends on its own writes:
the IDs of records it has just written, the queries the library writers
(`US_ConvertIO`, `US_TimeState`, `US_BufferComponent`, `US_ExtProfile`) make
themselves, the names of model and noise records of a run it renamed, and one
last `get_experiment_info_by_runID` per new run, right before the run's row is
written: a run of that ID that another session created since the preflight
fails the import (import again to have the run renamed) instead of being
duplicated.

Raw data and edits are written the way the rest of UltraScan writes them, with
`US_ConvertIO`: `writeRawDataToDB()` for a run's raw data rows and blobs, its
cell rows and its experiment-solution links, and `findRawDataId()`,
`createEditedData()` and `uploadEditedDataBlob()` for the edits. A run's speed
profile is read from its experiment XML and stored with the run.

A database import writes nothing into the local disk store. Several library
writers keep a local copy of what they store (`US_Project::saveToDB()`,
`US_Buffer::saveToDB()`, `US_Analyte::write()`, `US_Solution::saveToDB()`,
`US_Model::write()`, `US_Experiment::saveToDB()`, `US_Rotor::readLabsDB()`), so
the import writes those records with the same stored procedures, in the same
order and with the same arguments, but without the copy. For a buffer that is
`new_buffer` and one `add_buffer_component` per component; for an analyte
`new_analyte` and, for DNA and RNA, `set_nucleotide_info`; for a noise record
`new_noise`, with the model's ID and the ID of the edit the model was fitted
to, without the lookups `US_Noise::write()` makes (and without its update of a
noise record that happens to have the GUID). `US_Buffer::saveToDB()` and
`US_Analyte::write()` join a caller's transaction and then leave their disk
copy out, but they still update a record of the same GUID whoever owns it,
where the import only creates.

The extinction spectrum of a buffer, analyte or solution is stored as its
extinction profile (`new_eprofile`, through
`US_ExtProfile::create_eprofile()`; a solution's under the component type
`Sample`, as `US_Solution::saveToDB()` stores it), made of the values the
bundle carries and nothing else: those of its `spectraPayload`, at full
precision, or, in an older bundle without one, the `<extinction>` elements of
the record's own XML. `US_Analyte`'s reader adds the extinction at 280 nm that
it computes from a protein's sequence; that value is not part of the record,
so a protein without a spectrum gets no profile, and a measured spectrum keeps
the points it has. An older bundle stored a protein as `US_Analyte` wrote it,
computed point included: a lone point at 280 nm in such a bundle's analyte
XML is taken for that computed value and not stored (a measured 280 nm value
inside a spectrum of more points is kept). Its values have to be finite
numbers, or the bundle is refused before anything is written. A sequence is
stored exactly as the bundle holds it — a FASTA header, residue numbers and
line breaks are the analyte's own — in a database as on disk.
When an analyte is compared with one of the target, both are put in the same
terms: the sequence without the framing `US_Analyte`'s old writer put around
it (a newline, pieces of 80 characters each with a newline, a last newline —
taken off only when the text is exactly that, however many round trips
piled it up), and the extinction
without the 280 nm value computed from the sequence where that is the value
held. A buffer's component concentrations are taken at full
precision from the `concentration` of each component in its
`componentsPayload`, matched by the source's component ID (an older bundle has only the buffer file's five
decimals); the database column is a `FLOAT`. A disk store has no place for a
solution's profile, so a disk import leaves it out and says so.
The library writers store a profile only for a spectrum they were told is new,
which one read from a file never is. The import's only files are work copies
in the bundle's own staging directory, removed with it.

A disk import writes files as it goes. When it fails part way, the files it
already wrote stay, and the error lists them.

An import unpacks the bundle into a private staging directory under the
temporary directory, and holds a lock file there from the moment the
directory is made until everything else in it has been removed. The import
installs no signal handlers: a signal that stops it (SIGTERM, SIGINT, SIGHUP,
SIGKILL, a crash) stops it as it would any program, a signal the process was
started with ignored stays ignored (`nohup` protects an import), and a
database import's open transaction is rolled back by the server when the
connection goes. The directory of a stopped import keeps the lock of a
process that is gone, and the next import sweeps it, together with every
staging directory without a lock that has not changed for two days.

An export (and a preview or dry run) stages in a directory of the same kind,
locked with `export.lock` from the moment it is made, and sweeps first: a
staging directory whose locks no running process holds — an export or import
stopped by a signal — is removed, a running one's never
(`US_DataPubBundle::sweepStaleStaging()`).

A model's variance and meniscus are columns of its database row as well as
attributes of its XML, where `US_Model` writes six significant digits. A
`variance` and `meniscus` attribute of the model's manifest entry win over the
XML's and are written with all their digits; without them the XML's values are
used. An export writes both: from the database the values of the model's row
(which the stored XML need not hold), from disk those of the model file.

A few columns of the source's rows have no place in a payload. The import
writes them from optional attributes of the record's manifest entry, and
without them as it always did:

| Attribute | Of | Written to | Without it |
|---|---|---|---|
| `private` (`0` or `1`) | buffer | the buffer's private flag | private, as `US_Buffer::saveToDB()` makes a buffer |
| `comment` | edit | `editedData.comment` | empty (as `us_edit` stores an edit) |
| `label`, `comment` | raw data | `rawData.label`, `rawData.comment` | the run's label and comment, as `us_convert` writes raw data |
| `spectrum` (may be empty) | analyte | the analyte row's `spectrum` column | its first extinction (or refraction, fluorescence) point, as `US_Analyte` writes it |

An export from a database writes them from the source's rows
(`get_buffer_info`'s `private`, `get_rawData`'s `label` and `comment`,
`get_editedData`'s `comment`, `get_analyte_info`'s `spectrum`, the last also
when it is empty). A disk store has none of these columns, so an export from
disk leaves the attributes out.

The raw data rows of a run are written in one call (`US_ConvertIO`), which
gives all of them one label and comment: the run's raw data records have to
agree on theirs, or they are written with the run's, and the log says so.

A **dry run** reads the target and decides everything, but opens no
transaction and writes nothing — not even the output directory. Like the
import, it refuses a bundle with a number that is not finite (`nan`, `inf`)
in any attribute of a record or field of the manifest, naming the record,
the field and the value — whatever the target. Into a
database it makes the decisions the writers make as they go: it stages each
run and checks its triples against the bundle, reads its RI profile, resolves
its project and its hardware (so `--strict-hardware` fails a dry run that
would need a substitute, as it fails the import), leaves out a rotor
calibration whose rotor the target lacks, and checks that every solution and
time state has a run of the import and every triple its solution.

It also checks, as the real import's preflight does before its transaction
opens, the rules the server would otherwise enforce only on the writes:

| Rule of the server | What the import does |
|---|---|
| `add_rotor_calibration` takes an administrator (user level 3) | A calibration the person logged in may not add is left out with a warning (`--strict-hardware` refuses it); an administrator's import records "no calibration experiment" as `-1`. The procedure dates the row itself (`NOW()`): the source's date is not kept |
| `create_buffer_component` takes user level 2 | A buffer component the target lacks is refused below that level |
| `new_solutionAnalyte` takes the investigator's own analyte (`analytePerson`), or an administrator | Another investigator's analyte of the bundle's GUID is not reused: the import makes a copy under a GUID of its own. One the bundle does not carry is refused |
| (none: no procedure checks it) | Another investigator's *private* buffer is not linked either: the import makes a copy. A public one, or the investigator's own, is reused |
| Raw data and solution rows name channel 1 (foreign keys) | A target without channel 1 is refused (when the channel table cannot be read, the log says the check could not be made) |
| `new_noise` needs an edit | A noise record that comes to no edit the bundle carries or the target holds is refused, never written with edit 0 |
| `new_experiment` takes an operator with a permit for the instrument | An operator without one is stood in for by the current investigator, or another operator who holds one, with a warning; with no permit holder at all the run is refused |
| Text goes into columns and procedure parameters of a character set (`latin1` in `us3.sql`'s schema, whatever the connection's), and a strict server refuses a character they cannot hold ("Incorrect string value") | The character set of every text parameter of the procedures and every text column of the tables a record type is written with is read from `information_schema` (the schema's default when it shows nothing), and a record whose text — any attribute or text of its XML, apart from an edit's and a time state's, which go into a BLOB, and its fields in the manifest — holds a character the narrowest of them cannot store is refused, naming the record, the field and the character (`α` into a `latin1` target, for instance; `é` fits) |

So a dry run that succeeds is an import that succeeds, short of what only the
writes can find: a lost connection, a record another session writes in the
meantime, and a server whose `create_buffer_component` has not been updated
and gives a new component a taken ID (it uses the row count plus one; the dry
run warns when that ID is taken, and the import is then rolled back). The
warning is one of the import's warnings, so `--strict-hardware` stops there.
It is not given when the server says its procedure counts nothing:
`SELECT us3_catalog_version()`, the version marker the updated procedures come
with, answers 1 or more (a server without it refuses the statement, which is
version 0), or the procedure's definition is readable (to its definer and an
administrator; anyone else reads none) and counts no rows. The run
hardware decisions (and so the operator check) are made as each run is
written; a strict import that has to substitute fails there and is rolled
back.

A buffer component the import adds is created with
`US_BufferComponent::saveToDB()`, which finds the new row in the component
table by its definition, never by the ID `create_buffer_component` answers
with: an unpatched server answers with the connection's previous insert ID.
The components of the bundle are matched to the target's with that class's
rule (`matchingID()`): the same name, unit, range and gradient flag as stored,
and coefficients equal to five decimals; of several such rows, the one of the
highest ID.

### Which project the data lands in

A bundle names the project its runs came from, but that is the *exporting*
installation's project. **Import into Project…** (or `--project-guid`) files
the data under a project this installation already has: every run is attached
to it, and the bundle's own project record — when it carries one — is reused
rather than created. The project has to exist in the target already, and in a
database it has to be one of the current investigator's; an unknown or foreign
one stops the import rather than being created. Switching the target between
disk and database clears the choice, since it was made from the other target's
list.

Left empty, the bundle decides as before: its project record is imported when
it carries one, and otherwise each run is attached to the project its own
experiment XML names, which is created from that reference only when the
target does not have it.

### How a record is matched

For every record in the manifest, in dependency order:

1. **Same GUID already in the target** → that is the same record. It is reused,
   and everything that depends on it is pointed at it. This includes a run.
   The database has no lookup of an experiment by GUID, and its experiment
   listings are an investigator's own, so a run is looked up by its run ID
   first — one query, which settles a run the investigator already holds — and
   only a run that leaves open is looked for in the investigator's whole
   experiment list (a run renamed in the target). A run the investigator does
   not hold, but whose raw data the database has, belongs to someone else: the
   import stops, rather than create a second experiment of that GUID or attach
   anything to another person's records. (`get_rawDataID_from_GUID` finds
   anyone's raw data for an admin and refuses it as "not permitted" to anyone
   else, which says the same.) A run of someone else's that has no raw data
   cannot be seen this way; `experiment.experimentGUID` is `UNIQUE` in the
   schema (`us3.sql`), so `new_experiment` refuses the second copy and the
   import is rolled back. All of this happens before the transaction opens.
2. **Name free** → the record is created, keeping its GUID from the bundle. A
   database allocates a fresh ID.
3. **Name taken by a record with a different GUID** → the properties of the two
   are compared. The bundle's copy is first rewritten to name the target's
   records (below), and both are re-serialized in a canonical form without the
   keys a copied record legitimately differs in: its own GUID, numeric record
   IDs and time stamps — an explicit list, so a property such as `solid` and
   the GUID of a parent record still count. Only the attributes that hold
   numbers are compared by value ("7.00000" is "7"); a name, description,
   label or serial keeps its text. A record the target holds without
   a GUID is never taken for the bundle's, and one that cannot be read to be
   compared fails the import rather than be taken for a different record.
   - **Properties match** → the policy decides: `reuse` points at the existing
     record, `rename` imports a renamed copy, `fail` stops the import.
   - **Properties differ** → the record is always imported under a new name.
     Reusing a record that differs would silently change what the imported data
     means, so `reuse` is not offered. `fail` still stops the import.
   - A run of the same ID and another GUID is another run; it is always
     renamed.

A run that is already in the database is not added to: when its raw data, a
solution of it or its time state is not there too, the import stops rather
than attach anything to a run it did not create — a dry run says so too.

An edit is stored without a comment, as `us_edit` and `us_import_run` store
one (its file name already names the triple), unless its manifest entry
carries the source's (`comment`, above).

Renaming changes the name inside the payload; the GUID is untouched, so the
record's dependants follow it. Auto-generated names are `<name> (imported)`,
then `<name> (imported 2)`, and so on until one is free (after a thousand,
`<name>-` and eight random hexadecimal digits, checked like the others). A
buffer is compared and renamed into a database under the description it is
stored with, without the `  [M]` marker of a manually entered buffer. A run
is renamed
`<runID>-imported` (the suffix with anything a run ID cannot hold replaced by
`_`), and everything that carries the run ID follows it: the raw data, edit
and time state file names, the `runid` inside each edit, and the descriptions
of models and noise records named after the run.

### RI profiles and buffer components

An RI run's intensity profile travels as a file of its own. A disk import
puts it back beside the experiment XML as `<runID>.RIProfile.xml`, under the
run's new ID when it was renamed; a database import stores it in the
experiment row, as `US_Experiment::saveToDB()` would.

A buffer names its components by the source installation's IDs, which mean
nothing in the target, so the bundle carries their definitions. Each
component is matched in the target's component table by name, unit, range,
gradient forming and coefficients (to the five decimals the tables store), and
the buffer is pointed at the target's ID -- of several rows of that
definition, the highest. Two buffers that differ only in
their components are different buffers: the comparison of a buffer with one
the target has keeps the component IDs, both in terms of the target's table.

* **Database:** a component the database does not have is added to its table
  inside the import's transaction, and the log says so. A row of the
  database's table that cannot be parsed (not six coefficients per field) has
  nothing to do with the bundle; it is skipped with a note.
* **Disk store:** the components of a disk store are those of the
  installation's `etc/bufferComponents.xml`, which is where `US_Buffer` looks
  a component up whatever data directory it reads — `--output-dir` does not
  change that. An import never writes that table. Every component of a buffer
  it creates has to be in it already, with the same definition; otherwise the
  import is refused before anything is written, naming the components. Add
  them with the buffer editor first, or import into a database, which takes
  them along. A buffer the disk store already holds by GUID is reused as it
  is.

### Pointing records at the target's records

When a record was matched to a target record of another GUID, every payload
that names it is rewritten to name the target's: a solution's buffer and
analytes, a model's edit (and the analytes of its components), a noise
record's model, an edit's raw data, and in a run's experiment XML its project,
solutions, centerpieces and rotor calibration.

Numeric IDs are never carried over. A database allocates its own. In a disk
store a record the import writes carries the ID `-1`, and a reference names the
ID the target's record has, or `-1`. A rotor calibration written to disk names
the target's rotor of the same GUID, or none. It is the exception to `-1`: a
disk store finds a run's calibration by the ID the run's XML names, so the
calibration gets one no calibration of the store's `rotors` directory has (the
highest there plus one), and the runs of the bundle name it. Exported from
the store again, the run still has its calibration.

### Order of replay

The manifest lists records in the declared section order. The import replays
them in an order worked out from the dependencies: those the target has (listed
below) and every dependency the manifest's records name, apart from a
solution's on its run in a disk store, where it runs the other way. Each record
type comes after every type it needs; a bundle whose dependencies go round in a
circle is refused. With the dependencies of a normal bundle the order is:

* **Database:** project, rotor calibration, centerpiece, buffers, analytes,
  experiment, solutions, raw data, time state, edits, models, noise. The
  experiment goes in before the solutions because a database allocates the
  experiment ID a new solution record is associated with — always the run the
  bundle says the solution belongs to.
* **Disk store:** project, rotor calibration, centerpiece, buffers, analytes,
  solutions, experiment, raw data, time state, edits, models, noise. The
  solutions go in first because the run's experiment XML names them, and that
  file is rewritten as it is written out to name the records of the target.
  An experiment XML that cannot be rewritten stops the import.

### A bundle without a project

Every experiment in the database belongs to a project, so a bundle exported
with `--no-project` still has to land somewhere:

* The project GUID the run names is looked up in the target. When it is there,
  the run is attached to it and nothing is changed.
* When it is not, a project record is created from what the run itself names
  (GUID and description), and the log says so.

Importing to a disk store keeps the run's project GUID and description; the
project ID becomes the target's ID for that project, or `-1` when the target
does not have it.

### Hardware: matched, substituted or left out

Centerpieces, rotors, rotor calibrations, labs, instruments and operators are
the site's hardware. The import matches them and never invents them:

* A **centerpiece** is matched by GUID, then by an identical entry of the same
  name in the target's table, and the runs are pointed at the target's serial
  number. It is never created.
* A **rotor calibration** is created under the target's rotor of the same rotor
  GUID. Without that rotor it is *not imported*.
* A run's **rotor and calibration** are the imported calibration and its rotor;
  its **lab** is the lab that owns that rotor; its **instrument** is the lab's
  instrument of the same serial number; its **operator** is the person of the
  same GUID.

When the target has no match, another of its records *stands in*: the target's
first centerpiece, rotor or calibration, the lab's first instrument, the
current investigator. Such a record is reported as **substituted** (or **not
imported**), never as created, and every substitution is a warning: in the
log, on the command line's error output, and in the window's closing message.
`--strict-hardware` makes a substitution fail the import instead. A target with
no rotor, calibration or instrument at all cannot take the run.

A disk store has no lab, instrument or operator tables of its own (those are
database records), so a run imported to disk keeps the lab, instrument and
operator its experiment XML names; `US_Convert` resolves them when the run is
uploaded to a database.

### The window

1. **Import data into** — the disk/database selector.
2. **Select Bundle…** and **Inspect** — unpacks the bundle, reads and checks the
   manifest, verifies every payload digest and fills the contents tree. Editing
   the bundle path afterwards means the bundle has to be inspected again.
3. **Disk Target Folder…** — where a disk import writes. Left empty, the
   UltraScan3 data and results directories are used. Set to a folder, the
   import builds `<folder>/data/...` and `<folder>/results/...` there.
4. **On a name conflict** — the policy, and **Ask me each time**, which opens a
   dialog per conflict showing whether the two records match and offering
   *Use the Existing Record*, *Import Under a New Name* (with the name to give
   it) or *Abort the Import*. The dialog can apply its answer to every further
   conflict of the same record type. Escape or *Abort* cancels the import.
5. **Dry run** decides everything and writes nothing. **Verify payload digests**
   checks the bundle before the first write.
6. **Import Bundle**, then the log and the counts of created, reused, renamed,
   substituted and not-imported records, with the warnings. While an import or
   an inspection runs — until its closing message has been dismissed — the
   tab's controls are disabled, the export tab cannot be used and the window
   does not close. The end of an import leaves the options as they were,
   the chosen project included: only switching the target clears that.

### Command line

```
us_data_publication --mode import --bundle <file.tar.gz> [options]
```

| Option | Meaning |
|---|---|
| `--target db\|disk` | Where the records are written (default: `db`) |
| `--output-dir <dir>` | Disk target root; without it the UltraScan3 data and results directories are used |
| `--project-guid <guid>` | Attach the imported runs to this project of the target; it has to be there already |
| `--on-conflict <policy>` | `reuse`, `rename` or `fail` (default: `reuse`) |
| `--on-conflict-<type> <policy>` | The policy for one record type |
| `--rename-suffix <text>` | Suffix for auto-renamed records (default: `imported`) |
| `--no-verify` | Skip the payload digest check; the only way to import a bundle without digests |
| `--strict-hardware` | Fail rather than stand another rotor, calibration, centerpiece, instrument or operator in for a missing one |
| `--list` | Print the manifest and stop |

A database import settles the master password first, before the bundle is
unpacked; without one it stops with a single error that names the ways to
give it (`--db-password-file`, `US3_DB_PASSWORD`).

The closing line counts the records created, reused, renamed, substituted and
not imported; warnings go to the error output. A failed import says what it
left behind: a rolled-back transaction, or the files a disk import had already
written.

Examples:

```bash
# Into the configured database, asking nothing, renaming anything that clashes
us_data_publication --mode import --bundle run3_full.tar.gz \
    --target db --on-conflict rename --non-interactive

# Into a fresh folder, to look at before committing to anything
us_data_publication --mode import --bundle run3_full.tar.gz \
    --target disk --output-dir ~/inspect/run3

# Into a project of this installation, whatever the bundle names
us_data_publication --mode import --bundle run3_full.tar.gz --target db \
    --project-guid 6f1d2b7e-5c44-4f0a-9a01-2b8e7c3d4f55

# Reuse matching solutions and buffers, but never reuse a model
us_data_publication --mode import --bundle project7.tar.gz --target db \
    --on-conflict reuse --on-conflict-models rename

# Only into a database with all the hardware the runs used
us_data_publication --mode import --bundle run3_full.tar.gz --target db \
    --strict-hardware

# What is in this bundle?
us_data_publication --mode import --bundle project7.tar.gz --list
```

### Common options

| Option | Meaning |
|---|---|
| `--no-ui` | Run without the window (implied by `--mode`) |
| `--db-password-file <file>` | Read the master password for database access from the first line of a file. On Unix a file that its group or other users can read is warned about (`chmod 600` it) |
| `--db-password <pw>` | The master password itself. Other users of the machine can see it in the process list, so the program warns; prefer the file or `US3_DB_PASSWORD`, which is used when neither option is given. Without any of them an interactive run prompts on the error output, without echoing (an interrupted prompt puts the terminal back); a `--non-interactive` run stops with exit code `2`, and so does a Windows run whose input is not a console, since the password could not be read there without showing it |

From a file, the environment and the prompt alike only the line end that ends
the password — one `\n`, `\r\n` or `\r` — is removed; spaces are part of it,
and all three are read as UTF-8 (the environment variable as the text the
system holds, so a non-ASCII password survives on Windows too). A password
file that cannot be read, and an empty password from the file, the environment
or the prompt, is reported once and the run exits with `1`; no password at all
is a usage error (`2`). `US3_DB_PASSWORD` that is set to nothing
(`US3_DB_PASSWORD=`) is an empty password, not a missing one: exit `1`, no
prompt. A wrong master password is said to be wrong — it is checked against
the hash the installation keeps and against the database password stored for
the default database before any connection is made — instead of surfacing as
the server's "Access denied … (using password: NO)". The prompt keeps the terminal quiet
across Ctrl-Z: a stopped and continued prompt goes on reading without echo,
and a signal that does not end the program does not leave it echoing either.
| `--dry-run` | Decide everything, write nothing |
| `--non-interactive` | Never prompt; fail instead of asking |
| `--verbose` | Report every step |
| `-h`, `--help` | Usage |
| `--version` | Program version |

Exit codes: `0` success, `1` the export or import failed (a database import
is then rolled back), `2` the arguments were wrong. An import that substituted
hardware still exits with `0`, and says so on the error output. An option is
never taken as the value of the option before it: `--bundle --dry-run` is an
error. A value that starts with `--` can be given as `--comment=--draft`.

## Round trip

```bash
# On the machine that produced the data
us_data_publication --mode export --source db \
    --experiment-id Demo_2024_Run3 --max-scope noise \
    --comment "Supplement to doi:10.0000/example" \
    --bundle demo_run3.tar.gz

# On the machine that receives it
us_data_publication --mode import --bundle demo_run3.tar.gz \
    --target disk --output-dir ~/ultrascan --verbose
```

The second command prints one line per record and a closing count. Re-running
it reports every record as *reused*: the GUIDs are already in the target and
the payloads already match, so there is nothing left to do and nothing is
written twice.

## Tests

`test/programs/us_data_publication/` builds the non-GUI half of the program
straight into a GoogleTest binary, so the tests exercise the sources the
program ships:

```bash
cmake -S . -B build -DUS3_PROFILE=TEST
cmake --build build --target test_us_datapub
ctest --test-dir build -L gtest-unit-programs-datapub --output-on-failure
```

The suite covers the manifest vocabulary and its YAML round trip, the payload
and property digests, the rotor-calibration and centerpiece payload formats,
renaming a record inside its payload, packing and unpacking a bundle (and the
packs and bundles that are refused), exporting data only and exporting models
with their dependencies, what an export refuses and what it carries besides the
records (time state definitions, RI profile, buffer components), the export
arguments of the command line, the catalog's database queries against the
`IUS_DB2` mock, and importing into a
disk store along the create, reuse and rename paths, including the GUID remap
that a reused record forces into the payloads that name it. Crafted bundles
check that the import refuses paths outside the bundle, unusable run IDs,
payloads without a digest or of another GUID, and tampered time state
definitions. The database import runs against the `IUS_DB2` gmock mock
(`datapub_fake_db.h`), which pins down its single transaction, the rollback on
a failure part way, the speed profile, hardware substitution and a second
import of the same bundle writing nothing. The fake scopes its lookups and
listings as the stored procedures do: the GUID lookups of buffers, analytes,
edits, models and noise find anyone's record, those of projects, solutions
and raw data refuse someone else's unless the person is an admin, and the
listings are the given investigator's. It keeps an owner per GUID and a
unique experiment GUID, forgets what a transaction wrote when it is rolled
back (or the connection dropped), can have a procedure commit implicitly,
can change the database as the transaction begins, and keeps the bytes of
every blob. The tests use it for the run lookups made before the
transaction and the lookups the transaction must not make, a run ID taken
while the import ran, an implicit commit, records of another investigator
(reused, or named as a parent), the extinction profiles, a dry run that
decides what the import would, and a local disk store left byte for byte
and time for time as it was. The disk import tests name a component table of
their own (`Options::componentTable`) and check that neither it nor the
installation's table is changed.
