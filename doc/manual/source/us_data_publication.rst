=====================================
Data Publication: Export and Import
=====================================

.. toctree::
  :maxdepth: 3

.. contents:: Index
  :local:


**Data Publication** packs a complete UltraScan-III data set into a single
``.tar.gz`` bundle and replays that bundle into another UltraScan-III
installation. Use it when a data set has to leave the machine it was produced
on: a publication supplement, a hand-over to a collaborator, or an archive copy
that stays readable when the database does not.

A bundle is self-contained. It carries the project, the experiment, the raw
data, the rotor calibration, the centerpieces, the buffers, the analytes, the
solutions, the edits, the models and the noise records, in the order in which
they have to be re-created, together with a ``manifest.yaml`` that says what is
in the bundle and what depends on what.

The module opens with two tabs, **Export** and **Import**, so that it is always
clear which of the two jobs is being done. Each tab begins with its own
disk/database selector: on the Export tab it says where the records are read
*from*, on the Import tab where they are written *to*.

The same program also runs on the command line. See
:ref:`datapub-command-line` below.


The dependency chain
====================

Everything the module does follows one order::

  project -> experiment -> rawData -> rotorCalibration -> centerpiece
          -> buffers -> analytes -> solutions -> edits -> models -> noise

An export always carries a *prefix* of that chain, so that every record in a
bundle can be re-created from records that appear earlier in the same bundle.
Asking for the models therefore also brings the edits, the solutions, the raw
data, the experiment and the project.

Raw data is the one exception to the declared order: it cannot be re-created in
a target installation without the solutions its cells and channels refer to, so
a scope that reaches the raw data is automatically raised to the solutions. The
log says so when it happens.

Time state data is not a scope of its own. It travels with the raw data of its
run, and can be left out with the **Include time state** check box.


Identifiers
===========

Every record carries three identifying pieces, and they are not
interchangeable.

The **ID** (``projectID``, ``experimentID``, ``rawDataID``, ``editedDataID``,
``modelID``, ``noiseID``, ...) is a database key. It is only meaningful inside
the installation the bundle came from, and records read from a local disk store
frequently carry the placeholder ``-1``. It is written to the manifest because
it makes a bundle traceable, and for nothing else. Numeric IDs are never
carried over on import: the database allocates its own.

The **GUID** (``projectGUID``, ``experimentGUID``, ``rawDataGUID``,
``editedDataGUID``, ``modelGUID``, ``noiseGUID``, ...) is what an import matches
on, and what ties a record to its parents. GUIDs are generated by the client
and travel unchanged.

The **name** is what a person recognizes the record by, and what the conflict
rules compare: the ``runID`` of an experiment, the ``filename`` of a raw-data
triple or an edit, and the description of a project, buffer, analyte, solution,
model or noise record.


Exporting
=========

The Export tab works from the top down.

**Export data from**
  The disk/database selector. Changing it clears the selection, because a run
  in one source is not the same record as a run of the same name in the other.
  When the source is the database, edits, models and noise records are read
  from their database records, not from whatever happens to be in the local
  directories.

**Select Project**
  Opens the standard :doc:`project <us_project>` dialog. At most one project
  can be chosen. Choosing one drops any already selected run that does not
  belong to it.

**Select Experiment(s)**
  Opens the run selection dialog. When a project is selected the dialog offers
  only that project's runs; without a project it offers every run. Selecting
  runs is enough on its own -- a project is not required, and one is adopted
  from the first run when none was picked.

**Experiments, raw data and edits**
  A tree of check boxes, ``run -> rawData -> edit``. The buttons underneath are
  **All Raw**, **No Raw**, **Latest Edit**, **All Edits** and **No Edits**.
  Checking an edit checks its raw data; unchecking raw data unchecks the edits
  below it.

**Selected models and noise**
  A second tree, ``run -> rawData -> edit -> model -> noise``, filled by
  **Select Models...**, which opens the model loader pre-filtered to the
  selected runs. After models are picked the module offers to select the edits
  they were fitted to, because a model cannot be imported without its edit.
  Unchecking raw data or an edit that a selected model needs asks whether to
  drop those models or to keep the selection.

  The noise records of the selected models are selected automatically. When the
  *noise dialog* preference is set (:doc:`UltraScan Configuration <config>`,
  Advanced), **Select Noise...** opens the noise loader instead so that the
  records can be picked by hand.

**Export up to**, **Include time state**, **Comment**, **Bundle file**
  The scope, whether the runs' time state travels along, a free-text comment
  stored in the manifest, and where the bundle is written.

**Summary** and **Details...**
  The counts of experiments, raw data, edits, models and noise records.
  **Details...** shows the manifest that would be written, without copying a
  single byte of experimental data.


The bundle
==========

A bundle is a gzip-compressed tar archive with ``manifest.yaml`` at its root
and one directory per record type::

  bundle.tar.gz
  |-- manifest.yaml
  |-- project/<projectGUID>.xml
  |-- experiment/<runID>.<runType>.xml
  |-- rawData/<runID>/<runID>.<runType>.<cell>.<channel>.<wl>.auc
  |-- timeState/<runID>/<runID>.time_state.tmst
  |-- rotorCalibration/<rotorCalibrationGUID>.xml
  |-- centerpiece/centerpiece_<serial>.xml
  |-- buffers/<bufferGUID>.xml
  |-- analytes/<analyteGUID>.xml
  |-- solutions/<solutionGUID>.xml
  |-- edits/<runID>/<runID>.<editID>.<runType>.<cell>.<channel>.<wl>.xml
  |-- models/<modelGUID>.xml
  `-- noise/<noiseGUID>.xml

Payload files are exactly the files UltraScan-III uses in a local disk store,
so a bundle can be opened and read with ordinary tools.

The manifest is a small subset of YAML: a block of scalar header keys
(``version``, ``created``, ``generator``, ``source``, ``scope``,
``bundleGUID``, ``comment``), then one list per record type. Each entry names
the record's ID, GUID and name, the path of its payload inside the bundle, the
**SHA-256 digest of that payload file**, and the GUIDs of the records it
depends on. A section that was in scope but has nothing in it is written as
``[]``, so a reader can tell "exported and empty" from "not exported at all".


Importing
=========

An import replays a bundle into the database or into a local disk store,
whichever the selector at the top of the Import tab says. The database
connection is the one already configured in UltraScan.

**Nothing in the target is ever overwritten.** A record that is already there
is either pointed at or imported again under a new name.

For every record in the bundle, in dependency order:

* **The same GUID is already in the target.** That is the same record. It is
  reused, and everything that depends on it is pointed at it.
* **The name is free.** The record is created, keeping its GUID. A database
  allocates a fresh ID.
* **The name is taken by a record with a different GUID.** The properties of
  the two are compared, ignoring the identifiers and time stamps, so that two
  copies of the same record made in different installations compare equal.

  * *Properties match*: the conflict policy decides -- **reuse** points at the
    existing record, **rename** imports a renamed copy, **fail** stops the
    import.
  * *Properties differ*: the record is always imported under a new name.
    Reusing a record that differs would silently change what the imported data
    means, so reuse is not offered. **fail** still stops the import.

Renaming changes the name inside the payload and nothing else; the GUID is
untouched, so the record's dependants follow it. Auto-generated names are
``<name> (imported)``, then ``<name> (imported 2)``, and so on. A run is
renamed ``<runID>-imported``, and its raw data, edit and time state files are
renamed to match.

With **Ask me each time** set, each conflict opens a dialog that shows whether
the two records match and offers *Use the Existing Record*, *Import Under a New
Name* -- with the name to give it -- or *Abort the Import*. The dialog can
apply its answer to every further conflict of the same record type.

**Dry run** decides everything and writes nothing. **Verify payload digests**
checks the whole bundle before the first write; a bundle whose payloads do not
match their digests is refused.

**Disk Target Folder** is where a disk import writes. Left empty, the
UltraScan-III data and results directories are used. Set to a folder, the
import builds ``<folder>/data/...`` and ``<folder>/results/...`` there, which
is a good way to look at a bundle before committing to anything.

Reference data the import does not create
-----------------------------------------

* **Centerpieces** are the reference table an installation ships with, not user
  data. The import matches the bundle's centerpiece against the target's table
  and remaps the serial number; it never adds a row. When the target has no
  matching entry, the run keeps the serial number from the bundle and the log
  says so.
* **Rotors, labs, instruments and operators** are site hardware. A rotor
  calibration is attached to the rotor in the target with the same rotor GUID.
  When an experiment's rotor, instrument or operator is not in the target
  database, the import falls back to the target's first rotor, to the lab's
  first instrument and to the current investigator, and reports each
  substitution. Check those runs afterwards if the hardware matters.


.. _datapub-command-line:

Command line
============

Started without arguments the program opens the window. Started with
``--mode``, ``--no-ui`` or ``--help`` it runs on the command line, without
needing a display::

  us_data_publication --mode export --bundle <file.tar.gz> [options]
  us_data_publication --mode import --bundle <file.tar.gz> [options]

Export options
--------------

==============================  ==========================================================
``--source db|disk``            Where the records are read from (default: ``disk``)
``--project-id <id>``           Export this project, by database ID
``--project-guid <guid>``       Export this project, by GUID
``--experiment-id <run>``       Export this run; repeatable. Accepts a runID or an
                                experiment database ID
``--max-scope <scope>``         Export up to and including this record type
``--include-<scope>``           Raise the scope to this record type
``--model-guid <guid>``         Export only these models; repeatable
``--noise-guid <guid>``         Export only these noise records; repeatable
``--no-timestate``              Leave the runs' time state out
``--comment <text>``            Store a comment in the manifest
==============================  ==========================================================

Import options
--------------

=====================================  ===================================================
``--target db|disk``                   Where the records are written (default: ``db``)
``--output-dir <dir>``                 Disk target root; without it the UltraScan-III
                                       data and results directories are used
``--on-conflict <policy>``             ``reuse``, ``rename`` or ``fail``
``--on-conflict-<type> <policy>``      The policy for one record type
``--rename-suffix <text>``             Suffix for auto-renamed records
``--no-verify``                        Skip the payload digest check
``--list``                             Print the manifest and stop
=====================================  ===================================================

Common options
--------------

==============================  ==========================================================
``--no-ui``                     Run without the window (implied by ``--mode``)
``--db-password <pw>``          Master password for database access. ``US3_DB_PASSWORD``
                                is used when this is not given; without either, an
                                interactive run prompts on the terminal
``--dry-run``                   Decide everything, write nothing
``--non-interactive``           Never prompt; fail instead of asking
``--verbose``                   Report every step
``-h``, ``--help``              Usage
``--version``                   Program version
==============================  ==========================================================

Exit codes are ``0`` on success, ``1`` when the export or import failed and
``2`` when the arguments were wrong.

Examples
--------

Export everything about one run, read from the database::

  us_data_publication --mode export --source db \
      --experiment-id Demo_2024_Run3 --bundle run3_full.tar.gz

Export data only -- the chain down to the raw data, and with it the
solutions::

  us_data_publication --mode export --experiment-id Demo_2024_Run3 \
      --max-scope rawData --bundle run3_data.tar.gz

Import into a folder, to look at before committing to anything::

  us_data_publication --mode import --bundle run3_full.tar.gz \
      --target disk --output-dir ~/inspect/run3 --verbose

Import into the database, reusing matching solutions and buffers but never
reusing a model::

  us_data_publication --mode import --bundle project7.tar.gz --target db \
      --on-conflict reuse --on-conflict-models rename
