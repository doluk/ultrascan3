=====================================
Data Publication: Export and Import
=====================================

.. toctree::
  :maxdepth: 3

.. contents:: Index
  :local:


**Data Publication** packs a complete UltraScan-III data set into a single
``.tar.gz`` bundle and replays that bundle into another UltraScan-III
installation. Use it when a data set has to leave the machine it was produced
on: a publication supplement, a hand-over to a collaborator, or an archive copy
that stays readable when the database does not.

A bundle is self-contained. It carries the project, the experiment, the raw
data, the rotor calibration, the centerpieces, the buffers, the analytes, the
solutions, the edits, the models and the noise records, in the order in which
they have to be re-created, together with a ``manifest.yaml`` that says what is
in the bundle and what depends on what.

The module opens with two tabs, **Export** and **Import**, so that it is always
clear which of the two jobs is being done. Each tab begins with its own
disk/database selector: on the Export tab it says where the records are read
*from*, on the Import tab where they are written *to*.

The same program also runs on the command line. See
:ref:`datapub-command-line` below.


The dependency chain
====================

Everything the module does follows one order::

  project -> experiment -> rawData -> rotorCalibration -> centerpiece
          -> buffers -> analytes -> solutions -> edits -> models -> noise

An export always carries a *prefix* of that chain: asking for the models
therefore also brings the edits, the solutions, the raw data, the experiment
and the project. The manifest lists the records in the order in which every
record depends only on records listed before it (see `The bundle`_).

The project record is the one part that is optional. It is often not the
exporter's to publish, and the receiving installation usually keeps its own
project list. With the **Export the project record itself** check box cleared
the project is left out, but each run still names it, so an import can attach
the runs to a project the target already has.

Raw data is the one exception to the declared order: it cannot be re-created in
a target installation without the solutions its cells and channels refer to, so
a scope that reaches the raw data is automatically raised to the solutions. The
log says so when it happens.

Time state data is not a scope of its own. It travels with the raw data of its
run, and can be left out with the **Include time state** check box. A time
state is the binary ``.tmst`` together with the ``.xml`` of its field
definitions; a run whose time state has no definitions can only be exported
with the check box cleared.


Identifiers
===========

Every record carries three identifying pieces, and they are not
interchangeable.

The **ID** (``projectID``, ``experimentID``, ``rawDataID``, ``editedDataID``,
``modelID``, ``noiseID``, ...) is a database key. It is only meaningful inside
the installation the bundle came from, and records read from a local disk store
frequently carry the placeholder ``-1``. It is written to the manifest because
it makes a bundle traceable, and for nothing else. Numeric IDs are never
carried over on import: the database allocates its own.

The **GUID** (``projectGUID``, ``experimentGUID``, ``rawDataGUID``,
``editedDataGUID``, ``modelGUID``, ``noiseGUID``, ...) is what an import matches
on, and what ties a record to its parents. GUIDs are generated by the client
and travel unchanged.

The **name** is what a person recognizes the record by, and what the conflict
rules compare: the ``runID`` of an experiment, the ``filename`` of a raw-data
triple or an edit, and the description of a project, buffer, analyte, solution,
model or noise record.


Exporting
=========

An export walks the record chain -- experiment, raw data, edit, model, noise --
with the same catalog :doc:`Manage Data <manage_data>` browses with, so a
bundle sees exactly what the data manager sees. The experiments are listed
first and the chain of one experiment is read when the export needs it, which
is what keeps a multi-wavelength run from having to be read in full before the
first selection can be made.

A database that has not been updated still works. The catalog prefers stored
procedures added for it, and against a server that does not have them it
notices, says so on the status line, and falls back on the procedures UltraScan
has always had -- one query per record. The bundle is identical; collecting it
simply takes longer.

An export either is complete or fails, and then writes nothing: it stops when
there would be nothing in the bundle, when a record selected by GUID matches
nothing, when a run belongs to a project other than the one asked for, and when
any record it needs cannot be read -- the experiment, a solution with its
buffer and analytes, the rotor calibration, a centerpiece missing from the
centerpiece table, an undefined buffer component, a time state without its
definitions. A run without raw data is only a warning, unless none of the
selected runs has any. A raw data record or an edit read from the database
whose GUIDs are not the ones the catalog listed stops the export too, as does
a noise record selected by GUID whose model is not in the bundle, an
experiment XML that names another run ID or GUID than its run (a run
directory renamed by hand), and a value that is not a finite number
(``nan``, ``inf``, or a number too large for a double) anywhere in a record:
a spectrum, a buffer's pH, density, viscosity, compressibility or
concentrations, an analyte's vbar20 or molecular weight, a solution's common
vbar20, storage temperature or amounts. A missing project file on disk is
reported with the hint to leave the project out.

A run picked by name that the local results directory holds in more than one
directory -- a ``Copy of ...`` or ``Backup_...`` directory made by hand holds
the same files under the same names -- is refused, with a message naming every
directory: which of them is the run cannot be told, so keep only the directory
named after the run in the results directory. A run whose experiment XML
names a rotor calibration by an ID that, in the local rotor directory, belongs
to a calibration with another GUID is refused too, unless the calibration it
names by GUID is there: the other calibration's coefficients are not passed
off as the run's.

When the runs come with a project rather than by name, a run whose own records
do not hold together -- one of those problems, a channel without a solution,
a rotor calibration or centerpiece it names that is not there, a time state
without its definitions, an experiment XML that is missing or is not XML, a
run ID held in more than one directory, or an experiment, raw data or edit another run already brought into the
bundle (a run directory copied under another name, GUIDs and all) -- is left
out with a warning instead, and the rest of the project is exported. Its
models and their noise go with it, unless their edit is in the bundle after
all (with the run the copy was made from). A model or noise record selected by
GUID whose run is left out fails the export. A model or noise record that
holds a value that is not a finite number is left out with a warning, or
fails the export when it was selected by GUID. A database or disk that fails
still fails the export.

What was left out is always reported: the **Export Complete** box lists the
runs left out, the number of other records left out and the warnings (so do
the manifest preview and the box of an export that failed), and the command
line writes each warning to the error output, ``--verbose`` or not, and adds
``(left out: N run(s), M other record(s); see the warnings)`` to its last
line. The preview and a ``--dry-run`` are the export without the bundle: they
read, stage and check every record as the export does, so they list -- and
leave out -- exactly what the export would. The warnings count the runs left
out of a project once, whichever check left each one out.

A run's rotor calibration survives a trip through a disk store (database,
bundle, disk, bundle): the exported experiment XML names the calibration's
GUID as well as its ID, and an export from disk finds it by that GUID. A
model's variance and meniscus travel with every digit, in the manifest and in
the model payload. A noise record a model without noise of its own is carried
with names every such model of the bundle (``borrowedByModelGUIDs``).

An export or preview stopped by a signal leaves its staging directory with a
lock of a process that is gone; the next export or import removes it.

An export also refuses to write a bundle the import would refuse, and checks
it with the import's own rules before packing: every GUID of the manifest,
and every GUID an XML payload names (``guid``, ``...GUID``, the ``value`` of a
``...GUID`` element), has to be a GUID; a run type is one to eight letters or
digits; raw data, edits and the time state are named after their run. A legacy
record that breaks one is named in the message. Just before packing, the
staged files have to be exactly the manifest, its digest and the payloads it
names, each still matching its digest. When a whole project is exported, a run
of it that cannot be exported is left out with a warning instead; a run picked
by name is refused.

Only what the selected triples need goes into the bundle: the solutions and
centerpieces of their channels, and on disk an experiment XML without the
datasets of deselected triples or of triples whose ``.auc`` file is gone. An
RI intensity profile that is empty or does not parse is left out with a
warning, since an import would refuse it. A run whose database record names
no rotor calibration travels without one; the rotor's first calibration is
not assumed. The experiment XML names the run's investigator and operator by
GUID, as it does in a local store.

The Export tab works from the top down.

**Export data from**
  The disk/database selector. Changing it clears the selection, because a run
  in one source is not the same record as a run of the same name in the other.
  When the source is the database, edits, models and noise records are read
  from their database records, not from whatever happens to be in the local
  directories.

**Select Project**
  Opens the standard :doc:`project <us_project>` dialog. At most one project
  can be chosen. Choosing one drops any already selected run that does not
  belong to it. A project chosen without any run exports every run of the
  project, with everything up to the scope.

**Export the project record itself**
  Clear this to leave the project out of the bundle. The scope cannot be the
  project alone *and* leave the project out -- that would make an empty
  bundle.

**Select Experiment(s)**
  Opens the run selection dialog. When a project is selected the dialog offers
  only that project's runs; without a project it offers every run. Selecting
  runs is enough on its own -- a project is not required, and one is adopted
  from the first run when none was picked.

**Experiments, raw data and edits**
  A tree of check boxes, ``run -> rawData -> edit``. The buttons underneath are
  **All Raw**, **No Raw**, **Latest Edit**, **All Edits** and **No Edits**.
  Checking an edit checks its raw data; unchecking raw data unchecks the edits
  below it.

**Selected models and noise**
  A second tree of check boxes, ``run -> rawData -> edit -> model -> noise``,
  filled by **Select Models...**, which opens the model loader pre-filtered to
  the selected runs. After models are picked the module offers to select the
  edits they were fitted to, because a model cannot be imported without its
  edit. Unchecking raw data or an edit that a selected model needs asks whether
  to drop those models or to keep the selection.

  Every noise record of every selected model is checked automatically; uncheck
  the ones that should stay out. Unchecking a model unchecks its noise with it,
  and checking a noise record checks its model back on, because noise cannot
  travel without the model it belongs to. **Reload Noise** looks the records up
  again.

  A model with no noise of its own is not left without any. Noise is fitted to
  an edit, and a model made afterwards is run with the noise that was already
  there, so such a model travels with the newest noise of its edit that existed
  when the model was made -- one record of each type, since a run can carry a
  time-invariant and a radially-invariant record at once. Those rows are marked
  *(of this edit)* in the tree. The record still belongs to the model it was
  fitted to, so that model is exported too, and the bundle notes which model
  the record is carried for.

**Export up to**, **Include time state**, **Comment**, **Bundle file**
  The scope, whether the runs' time state travels along, a free-text comment
  stored in the manifest, and where the bundle is written.

**Summary** and **Details...**
  The counts of projects, experiments, raw data, edits, models and noise
  records. **Details...** shows the manifest that would be written, with what
  would be left out: every record is read and checked as the export does it,
  in a staging directory that is removed afterwards, so it takes as long as
  the export. Its progress is shown as the export's is, the window is locked
  meanwhile, and **Cancel** stops it. A preview that fails says "The export
  would fail" with the reason and the warnings.

**Export Bundle**
  Writes the bundle. While the export runs the tab cannot be changed, the
  Import tab cannot be opened, and a request to close the window is carried
  out once the export is done. **Cancel** stops the export at the next record;
  nothing is written. An existing file of the same name is replaced
  only once the new bundle is complete and has been read back and compared,
  file by file, with what was staged. The UltraScan ``tmp`` directory needs
  room for about twice the data plus the bundle while this happens.


The bundle
==========

A bundle is a gzip-compressed tar archive with ``manifest.yaml`` at its root
and one directory per record type::

  bundle.tar.gz
  |-- manifest.yaml
  |-- manifest.sha256
  |-- project/<projectGUID>.xml
  |-- rotorCalibration/<rotorCalibrationGUID>.xml
  |-- centerpiece/centerpiece_<serial>.xml
  |-- experiment/<runID>.<runType>.xml
  |-- experiment/<runID>.RIProfile.xml            (RI runs)
  |-- timeState/<runID>/<runID>.time_state.tmst
  |-- timeState/<runID>/<runID>.time_state.xml
  |-- buffers/<bufferGUID>.xml
  |-- buffers/<bufferGUID>.components.xml         (buffers with components)
  |-- buffers/<bufferGUID>.spectra.xml            (buffers with spectra)
  |-- analytes/<analyteGUID>.xml
  |-- analytes/<analyteGUID>.spectra.xml          (analytes with spectra)
  |-- solutions/<solutionGUID>.xml
  |-- solutions/<solutionGUID>.spectra.xml        (solutions with an extinction profile)
  |-- rawData/<runID>/<runID>.<runType>.<cell>.<channel>.<wl>.auc
  |-- edits/<runID>/<runID>.<editID>.<runType>.<cell>.<channel>.<wl>.xml
  |-- models/<modelGUID>.xml
  `-- noise/<noiseGUID>.xml

Payload files are exactly the files UltraScan-III uses in a local disk store,
so a bundle can be opened and read with ordinary tools. Three kinds are added
because a local store keeps that information elsewhere, or rounds it: the
definitions of a buffer's components (name, unit, density and viscosity
coefficients) together with the buffer's concentration of each at full
precision, since a buffer file names its components only by an
installation's own IDs and keeps a concentration to five decimals; the
radial intensity profile of an RI run, from a database copied as stored; and
the spectra of buffers, analytes and solutions at full precision
(``<US_DataPubSpectra>`` with one ``<spectrum type=...>`` per kind --
extinction, refraction, fluorescence -- of ``<point wavelength value>``
pairs), since a buffer file
keeps a wavelength to 0.1 nm and a value to five digits, an analyte file a
value to six, and a solution file has no place for its extinction profile.
``manifest.sha256`` holds the digest of the manifest in the format
``sha256sum -c`` checks.

Bundles are written in manifest format ``2``; format ``1`` bundles are read
too. A few development builds of format ``1`` listed a noise record carried
for a model without noise of its own under that model (with
``fittedToModelGUID``); such a bundle cannot be imported, and the import says
so and asks for the data to be exported again.

The manifest is a small subset of YAML in UTF-8: a block of scalar header keys
(``version``, ``created``, ``generator``, ``source``, ``scope``,
``bundleGUID``, ``comment``), then one list per record type, in the order::

  project -> rotorCalibration -> centerpiece -> experiment -> timeState
          -> buffers -> analytes -> solutions -> rawData -> edits
          -> models -> noise

in which every record depends only on records listed before it. Each entry
names the record's ID, GUID and name, the path of its payload inside the
bundle, the **SHA-256 digest of that payload file**, and the GUIDs of the
records it depends on -- a solution, for instance, on every one of its
analytes and on the experiment of every run whose channels it fills. Extra
files (the time state's definitions, the RI profile, the buffer components,
the spectra) are named by keys ending in ``Payload`` and have their digests
under the same key ending in ``Sha256``. Every value is quoted, with control
characters escaped (``\n``, ``\t``, ``\uXXXX``), so any description reads
back as it was written; an export checks that it does. A section that was exported
but has nothing in it is written as ``[]``; one that was not exported is left
out. A record without a GUID of its own -- a time state, an old rotor
calibration or centerpiece -- gets a name-based UUID derived from what
identifies it; for a calibration and a centerpiece that includes what the
record holds (coefficients, date, geometry), so two installations do not give
the same GUID to different records. A calibration gets the same GUID from the
database as from its local copy: only what both keep goes into it.

A manifest that is larger than 64 MiB, gives a key or section twice, has no
usable ``version``, nests a map under a key other than ``depends``, names a
path that could reach outside the bundle (absolute, ``..``, a drive prefix, a
backslash, ...), a file name Windows cannot hold (``CON``, ``aux.xml``, a
trailing dot or space, ``< > " | ? *``, control or invisible formatting
characters, more than 255 bytes), two paths that differ only in case, or an
unusable run ID, or lists a dependency after the record that needs it, is
refused.


Importing
=========

An import replays a bundle into the database or into a local disk store,
whichever the selector at the top of the Import tab says. The database
connection is the one already configured in UltraScan.

**Nothing in the target is ever overwritten.** A record that is already there
is either pointed at or imported again under a new name. A file of a disk
store's run directory is reused only when it is the file the import would
write -- a time state only together with the same field definitions -- and
anything else stops the import.

A bundle is checked as a whole before anything is written, and refused as a
whole when any check fails: every payload path has to stay inside the bundle;
every run ID has to hold only letters, digits, ``_`` and ``-`` (at most 80,
checked on the whole text, so not even a trailing newline passes) and every
run type one to eight letters and digits; every file name has to be safe on
every platform, and every run file has to start with its run ID; every GUID
the manifest names, and every GUID inside a payload, has to be a GUID; the
manifest has to match ``manifest.sha256`` and every payload -- including a
time state's field definitions, an RI profile and a buffer's component
definitions -- its digest, in either case (a payload without one fails too,
unless the check is switched off); every payload has to parse as its record
type and carry the GUID the manifest gives it; every buffer and analyte a
solution names, the model a noise record names, the edit a model names, the
raw data of an edit and the solution of every triple has to be in the bundle
or the target; and a bundle of the older format, without component
definitions, is refused when one of its buffers names components.

In a database, a project, solution, raw data, edit, model or noise record the
import would reuse or attach anything to has to be in the bundle or be one of
the current investigator's own. The database finds a record of these by its
GUID whoever owns it (an edit, a model or a noise record always, the others
for an administrator), so the import checks each against the investigator's
own list, and someone else's record stops the import before anything is
written. Buffers and analytes are shared, and reused whoever entered them.

A database import is one transaction: it is committed when every record is
in and rolled back on any failure, so a failed import leaves the database as
it was. (A stored procedure that commits by itself would end the transaction
early; the import then says that some records may have been kept.) Every
lookup that can be made in advance is made before the transaction opens: the
records of the bundle, the investigator's lists, the hardware, the buffer
components and the names a conflict compares with. Inside it run the writes,
the lookups of what the import has just written, and one last check of each
new run ID, so that a run of that ID created meanwhile by someone else fails
the import instead of being duplicated. Raw data and edits are written through
``US_ConvertIO``, the same writer the rest of UltraScan uses, and a run keeps
its speed profile. Buffers, analytes, models and noise are written with the
procedures the library writers use, but without the copy some of those
writers keep in the local disk store: a database import writes nothing there.
The extinction profile of a buffer or analyte holds the values its payload
holds, never the 280 nm value UltraScan computes from a protein's sequence. A
disk import writes files as it goes; when it fails, the error lists those it
had already written.

For every record in the bundle, in dependency order:

* **The same GUID is already in the target.** That is the same record -- a run
  too, whatever run ID it went by. It is reused, and everything that depends
  on it is pointed at it. A run is looked up by its run ID first and, only
  when that does not settle it, in the investigator's experiment list. A run
  that another investigator holds (its raw data is in the database, but it is
  not among the investigator's runs) stops the import: it is neither copied
  again nor added to. One without raw data cannot be seen that way, but the
  database holds each experiment GUID only once (``experimentGUID`` is
  ``UNIQUE``), so its second copy is refused and the import rolled back. A run
  the target already had is not added to either: its raw data, solutions and
  time state have to be there already.
* **The name is free.** The record is created, keeping its GUID. A database
  allocates a fresh ID.
* **The name is taken by a record with a different GUID.** The properties of
  the two are compared, ignoring the record's own GUID, the numeric IDs and
  the time stamps, so that two copies of the same record made in different
  installations compare equal. The GUIDs of parent records do count: the
  bundle's copy is first pointed at the target's parents, and a solution of
  another buffer is another solution.

  * *Properties match*: the conflict policy decides -- **reuse** points at the
    existing record, **rename** imports a renamed copy, **fail** stops the
    import.
  * *Properties differ*: the record is always imported under a new name.
    Reusing a record that differs would silently change what the imported data
    means, so reuse is not offered. **fail** still stops the import.

Renaming changes the name inside the payload; the GUID is untouched, so the
record's dependants follow it. Auto-generated names are ``<name> (imported)``,
then ``<name> (imported 2)``, and so on. A run is renamed
``<runID>-imported``, and everything that carries the run ID follows: the raw
data, edit and time state files, the run ID inside each edit, and the models
and noise records named after the run.

An RI run's intensity profile is restored beside its experiment XML on disk,
and stored with the experiment in a database. A buffer's components are
matched in the target's component table by name, unit, range, gradient
forming and coefficients. A database lacking one gets it added inside the
import's transaction. A disk store's components are the installation's
``etc/bufferComponents.xml``, which an import never changes: every component
of a buffer it creates has to be there already, or the import is refused
before anything is written. An edit is stored without a comment, as
``us_edit`` stores one, unless the bundle carries the source's. The bundle may
also carry a buffer's private flag (a public buffer stays public, so other
investigators use it rather than copy it), the raw data's label and comment,
and an analyte's spectrum column; without them the import writes what
UltraScan's own programs write.

A record matched to a target record of another GUID is renamed in every
payload that names it: a solution's buffer and analytes, a model's edit, a
noise record's model, and the project, solutions, centerpieces and
calibration of a run's experiment XML. Numeric IDs are never carried over: a
record written to a disk store carries ``-1``, a rotor calibration too, and
the runs name a calibration written to disk by ``-1`` and its GUID. (An
analysis looks the ID a run names up among the installation's calibrations,
where any real ID could be another rotor's; with ``-1`` the run's own
coefficients are used. An export from the store finds the calibration by its
GUID.)

With **Ask me each time** set, each conflict opens a dialog that shows whether
the two records match and offers *Use the Existing Record*, *Import Under a New
Name* -- with the name to give it -- or *Abort the Import*. The dialog can
apply its answer to every further conflict of the same record type. Escape
cancels the import. While an import or an inspection runs -- until its
closing message is dismissed -- the tab's controls are disabled, the export
tab cannot be used and the window does not close. Only switching the target
clears a chosen project; the end of an import does not.

**Dry run** decides everything and writes nothing, not even the target folder.
Into a database it makes the decisions the import would make as it writes:
it resolves each run's project and hardware (so a strict import that would
need a substitute fails its dry run too), leaves out a calibration whose
rotor the target lacks, and checks every run's triples and solutions. It
also checks, as the import does before it writes anything, what the server
would refuse: a rotor calibration only an administrator may add (it is left
out, with a warning), a buffer component the target lacks (adding one takes
user level 2), another investigator's analyte or private buffer (the import
makes a copy of its own instead), a target without channel 1, a noise record
without an edit, an operator without a permit for the instrument
(another one who holds a permit is recorded, with a warning), and text the
target's columns cannot store (a character such as "α" in a database whose
tables are latin1: the record, the field and the character are named). Into
any target, a number that is not finite ("nan", "inf") is refused. A dry run that
succeeds is an import that succeeds, short of a lost connection or a record
someone else writes in the meantime.
**Verify payload digests** checks the whole bundle before the first write; a
bundle whose payloads do not match their digests, or carry none, is refused.

**Disk Target Folder** is where a disk import writes. Left empty, the
UltraScan-III data and results directories are used. Set to a folder, the
import builds ``<folder>/data/...`` and ``<folder>/results/...`` there, which
is a good way to look at a bundle before committing to anything.

Which project the data lands in
-------------------------------

A bundle names the project its runs came from, but that is the *exporting*
installation's project. **Import into Project...** files the data under a
project this installation already has: every run is attached to it, and the
bundle's own project record -- when it carries one -- is reused rather than
created. The project has to be in the target already, and in a database it has
to be one of the current investigator's; an unknown or foreign one stops the
import rather than being created. **Clear** goes back to letting the bundle
decide, and so does switching between disk and database.

A bundle without a project
--------------------------

Every experiment in the database belongs to a project, so a bundle exported
without one still has to land somewhere. Without a project chosen, the project
GUID the run names is looked up in the target; when it is there the run is
attached to it, and when it is not, a project record is created from what the
run itself names. A disk import keeps the project GUID the run names; its ID
becomes the target's ID for that project, or ``-1``.

Hardware: matched, substituted or left out
------------------------------------------

Centerpieces, rotors, calibrations, labs, instruments and operators are site
hardware, which the import matches and never invents. A centerpiece is
matched by GUID or an identical entry of the same name; a rotor calibration is
created under the target's rotor of the same GUID, or not imported; a run's
lab is the one owning its rotor, its instrument the lab's instrument of the
same serial number, its operator the person of the same GUID.

When the target has no match, another of its records stands in -- the first
centerpiece, rotor or calibration, the lab's first instrument, the current
investigator. Such a record is reported as *substituted* or *not imported*,
never as created, and every substitution is a warning in the log, in the
closing message and on the command line's error output.
``--strict-hardware`` makes a substitution fail the import instead.


.. _datapub-command-line:

Command line
============

Started without arguments the program opens the window. Started with any long
option (``--mode``, ``--no-ui``, ``--help``, ...) it runs on the command line,
without needing a display, and reports arguments it does not understand::

  us_data_publication --mode export --bundle <file.tar.gz> [options]
  us_data_publication --mode import --bundle <file.tar.gz> [options]

Export options
--------------

==============================  ==========================================================
``--source db|disk``            Where the records are read from (default: ``disk``)
``--project-id <id>``           Export this project, by database ID
``--project-guid <guid>``       Export this project, by GUID
``--experiment-id <run>``       Export this run; repeatable. Accepts a runID or an
                                experiment database ID; a run ID that matches
                                exactly wins, and an ID only counts when one run
                                has it
``--max-scope <scope>``         Export up to and including this record type
                                (default: ``noise``, the whole chain)
``--include-<scope>``           Export up to and including this record type;
                                the deepest one given counts, and it may not
                                go beyond ``--max-scope``, within which it is
                                what is exported
``--model-guid <guid>``         Export only these models; repeatable
``--noise-guid <guid>``         Export only these noise records; repeatable
``--no-timestate``              Leave the runs' time state out
``--no-project``                Leave the project record out; the runs still
                                name it
``--comment <text>``            Store a comment in the manifest
==============================  ==========================================================

Import options
--------------

=====================================  ===================================================
``--target db|disk``                   Where the records are written (default: ``db``)
``--output-dir <dir>``                 Disk target root; without it the UltraScan-III
                                       data and results directories are used
``--project-guid <guid>``              Attach the imported runs to this project of the
                                       target; it has to be there already
``--on-conflict <policy>``             ``reuse``, ``rename`` or ``fail``
``--on-conflict-<type> <policy>``      The policy for one record type
``--rename-suffix <text>``             Suffix for auto-renamed records
``--no-verify``                        Skip the payload digest check; the only way
                                       to import a bundle without digests
``--strict-hardware``                  Fail rather than substitute missing hardware
``--list``                             Print the manifest and stop
=====================================  ===================================================

Common options
--------------

==============================  ==========================================================
``--no-ui``                     Run without the window (implied by ``--mode``)
``--db-password-file <file>``   Read the master password from the first line of a
                                file; on Unix a file others can read is warned about
``--db-password <pw>``          The master password itself; visible to other users in
                                the process list, so prefer the file or
                                ``US3_DB_PASSWORD``, which is used when neither is
                                given. Without any of them an interactive run prompts
                                on the error output without echoing; a
                                non-interactive run stops, and so does a Windows run
                                whose input is not a console. ``US3_DB_PASSWORD``
                                set to nothing is an empty password (exit 1), as is
                                ``--db-password ''``, and a wrong master password is
                                said to be wrong
``--dry-run``                   Decide everything, write nothing
``--non-interactive``           Never prompt; fail instead of asking
``--verbose``                   Report every step
``-h``, ``--help``              Usage
``--version``                   Program version
==============================  ==========================================================

Exit codes are ``0`` on success, ``1`` when the export or import failed (a
database import is then rolled back, and the error says what was left) and
``2`` when the arguments were wrong. An import that substituted hardware exits
with ``0`` and reports the substitutions on the error output. An export needs
``--experiment-id``, ``--project-id`` or ``--project-guid``; a ``--dry-run``
needs no ``--bundle``. An option is never taken as the value of the one before
it; a value starting with ``--`` is given as ``--comment=--draft``. An option
of the other mode -- ``--target`` with an export, ``--model-guid`` with an
import -- is refused with ``2``. Only the line end is taken off a password
read from a file, the environment or the prompt; spaces are part of it, and
all three are read as UTF-8. A password file that cannot be read is reported
once and an export exits with ``1``.

Examples
--------

Export everything about one run, read from the database::

  us_data_publication --mode export --source db \
      --experiment-id Demo_2024_Run3 --bundle run3_full.tar.gz

Export data only -- the chain down to the raw data, and with it the
solutions::

  us_data_publication --mode export --experiment-id Demo_2024_Run3 \
      --max-scope rawData --bundle run3_data.tar.gz

Export a whole project up to the models, without noise::

  us_data_publication --mode export --project-id 7 --include-models \
      --bundle project7.tar.gz

Import into a folder, to look at before committing to anything::

  us_data_publication --mode import --bundle run3_full.tar.gz \
      --target disk --output-dir ~/inspect/run3 --verbose

Import into the database, reusing matching solutions and buffers but never
reusing a model::

  us_data_publication --mode import --bundle project7.tar.gz --target db \
      --on-conflict reuse --on-conflict-models rename
